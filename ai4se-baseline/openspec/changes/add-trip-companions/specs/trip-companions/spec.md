# trip-companions 增量规格

## ADDED Requirements

### Requirement: 发现同行者并看到可解释的匹配原因

系统 SHALL 帮助用户在已有行程池上发现目的地、日期与兴趣相近的行程，并 MUST 以可理解的原因说明匹配结果，而非仅提供一个无解释的数字。

#### Scenario: 展示可解释的匹配原因
- **Given** 用户正在发现同行者场景查看候选行程
- **When** 系统按目的地、日期与共同兴趣评估相近程度
- **Then** 系统展示可解释的匹配原因（例如「目的地和日期相同，并且都喜欢摄影」）
- **And** 用户据此判断是否值得申请

#### Scenario: 匹配打分不可用时降级为筛选与共同兴趣提示
- **Given** 匹配打分作为增强能力暂不可用（时间不足降级）
- **When** 用户查找同行行程
- **Then** 系统至少提供按目的地与日期筛选，并提示与用户的共同兴趣
- **And** 系统不展示可能误导用户的百分比数字
- **And** 降级不影响用户提交同行申请

### Requirement: 提交与管理同行申请

系统 SHALL 允许用户对招募中且未满员的他人行程提交一句说明的同行申请，MUST 阻止不合规的申请，并允许申请者在被处理前取消。

#### Scenario: 提交同行申请
- **Given** 一条招募中且未满员的他人行程
- **When** 申请者填写一句申请说明并提交
- **Then** 系统生成一条状态为「待处理」的申请
- **And** 发布者能够看到该申请及申请者资料

#### Scenario: 不能申请自己发布的行程
- **Given** 用户正在查看自己发布的行程
- **When** 用户尝试对该行程申请同行
- **Then** 系统拒绝该操作，不生成申请

#### Scenario: 不能重复申请
- **Given** 用户对某行程已有一条尚未取消的申请
- **When** 用户再次对同一行程提交申请
- **Then** 系统拒绝重复申请

#### Scenario: 已满员或已结束的行程不能申请
- **Given** 一条状态为「已满员」或「已结束」的行程
- **When** 用户尝试申请同行
- **Then** 系统拒绝并提示该行程当前不可申请

#### Scenario: 处理前取消申请
- **Given** 一条状态为「待处理」的申请
- **When** 申请者在发布者处理之前取消该申请
- **Then** 申请状态变为「已取消」
- **And** 发布者不再需要处理该申请

### Requirement: 发布者处理申请并联动人数与状态

系统 SHALL 仅允许行程发布者接受或拒绝申请，接受成功后 MUST 增加已加入人数，并在达到计划人数上限时将行程置为「已满员」并停止接受新申请。

#### Scenario: 只有发布者能处理申请
- **Given** 一条待处理的申请
- **When** 非该行程发布者的用户尝试接受或拒绝
- **Then** 系统拒绝该操作

#### Scenario: 接受申请后建立连接并增加人数
- **Given** 发布者查看一条待处理申请
- **When** 发布者接受该申请
- **Then** 该行程已加入人数增加一人
- **And** 申请状态变为「已接受」
- **And** 申请者与发布者进入「已匹配」同行关系

#### Scenario: 达到人数上限后停止接受
- **Given** 一条行程的已加入人数已达到计划人数
- **When** 出现新的申请或发布者尝试继续接受
- **Then** 行程状态置为「已满员」
- **And** 系统停止接受新的申请

#### Scenario: 拒绝申请
- **Given** 发布者查看一条待处理申请
- **When** 发布者拒绝该申请
- **Then** 申请状态变为「已拒绝」
- **And** 申请者不进入已匹配关系

### Requirement: 匹配后的旅行前基础沟通

系统 SHALL 仅对已建立匹配关系的双方开放一对一文字沟通，消息 MUST 可保存并在刷新后重新读取；未匹配的用户 MUST 不能进入沟通。

#### Scenario: 未匹配用户不能进入沟通
- **Given** 两个尚未建立匹配关系的用户
- **When** 任一用户尝试进入与对方的行程沟通
- **Then** 系统拒绝进入

#### Scenario: 发送并持久化文字消息
- **Given** 已匹配的双方进入沟通页面
- **When** 一方发送一条文字消息
- **Then** 系统保存该消息并记录发送时间
- **And** 另一方在手动刷新或短轮询后能重新读取到该消息

### Requirement: 我的旅行聚合视图

系统 SHALL 提供「我的旅行」视图，让用户在一处按关系分组查看与自己相关的行程。

#### Scenario: 分组展示我的旅行
- **Given** 用户进入我的旅行
- **When** 页面加载完成
- **Then** 系统分组展示：我发布的、我申请的、已匹配的、已完成的、可分享体验的行程
- **And** 「可分享体验的」分组为 REQ-004 游后分享提供入口

### Requirement: 最低安全能力

系统 SHALL 提供取消申请、退出同行、举报入口等最低安全能力，MUST NOT 公开用户电话、证件与精确住址，并 MUST 展示首次见面与告知亲友的安全提示。

#### Scenario: 退出同行
- **Given** 一名已匹配的同行者
- **When** 其选择退出同行
- **Then** 同行关系被解除
- **And** 相关行程与我的旅行中的状态正确反映退出结果

#### Scenario: 使用举报入口
- **Given** 用户处于已匹配或申请相关的场景
- **When** 用户使用举报入口提交举报
- **Then** 系统记录该举报（MVP 不做处置闭环）

#### Scenario: 隐私保护与安全提示常驻
- **Given** 用户查看行程、同行或沟通相关页面
- **When** 页面涉及联系方式或线下见面
- **Then** 系统不公开用户的电话、证件与精确住址
- **And** 系统展示「首次见面请选择公共场所」与「重要行程请告知亲友」的安全提示
