# trip-plans 增量规格（refine-publish-route-map；MODIFIED = 在既有数量与顺序约束上追加编辑器、出行方式、降级与占位名约束；7 个基线场景原文保留）

## MODIFIED Requirements

### Requirement: 发布可被他人理解的旅行计划

系统 SHALL 允许已进入的演示用户发布一条旅行计划，并 MUST 按下列约束校验：标题 ≤ 40 字、目的地来自固定候选、出发与结束日期必填且结束不早于出发、至少两个途经点、计划人数 2–12（含发布者）、预算下限不高于上限、兴趣标签最多 5 个；集合区域、预算范围、兴趣标签与补充说明为选填。

途经点 MUST 通过「地图路线编辑器」录入，该编辑器 MUST 同时提供地图、关键字搜索与地图点选三种加点的入口，并 MUST 展示途经点列表、按当前顺序连成的路线、起点与终点标识、编号标记、总距离与总时长；途经点顺序 MUST 可由用户调整，调整后路线与编号 MUST 立即按新顺序重排；途经点 MUST NOT 超过 8 个，超过时 MUST 拒绝新增并给出可读提示。路线规划 MUST 由「生成旅行路线」按钮显式触发；首次生成完成后，增删途经点、调整顺序或切换出行方式 MUST 自动重新规划，无需用户再次点击。

出行方式 MUST 为「自驾 / 骑行 / 公共交通」三档，且 MUST 在编辑器内就地切换；切换后 MUST 重新规划路线；选择「公共交通」时 MUST 以目的地城市作为换乘搜索范围；本能力 MUST NOT 提供「步行」选项。发布页 MUST 显示「自驾 / 骑行 / 公共交通」，旅行地图探索页 MUST 保持「步行 / 驾车 / 骑行」，两处清单 MUST NOT 相互串味。路线服务不可用时，系统 MUST 按途经点顺序以直线示意并显式标注「示意 / 估算」，MUST NOT 静默降级、MUST NOT 展示空白地图，也 MUST NOT 把估算值表述为真实路线；降级提示 MUST 面向普通用户，MUST NOT 出现后端服务名、端口、代理或重载等实现细节。

发布请求 MUST 只提交按当前顺序排列的途经点名称数组与出行方式；编辑期的坐标 MUST NOT 进入请求体、响应体或数据库，本能力 MUST NOT 新增接口字段、端点、数据库迁移与契约版本。途经点名称 MUST 是用户可读的地名，MUST NOT 提交地图点选产生的坐标占位名（形如「地图选点 {经度}, {纬度}」）；存在占位名时 MUST 拒绝提交并提示改名。列表与详情 MUST 以提交顺序展示途经点；AI 推荐或参考行程预填的途经点 MUST 进入同一编辑器，并 MUST 可继续排序、删除与重新规划。

#### Scenario: 填写完整必填项后成功发布

- **Given** 用户处于发布行程表单
- **When** 用户填写全部必填项并提交
- **Then** 系统保存该行程，状态为「招募中」
- **And** 已加入人数计入发布者本人
- **And** 该行程出现在旅行灵感首页

#### Scenario: 选填项可留空

- **Given** 用户处于发布行程表单
- **When** 用户仅填写必填项、留空全部选填项并提交
- **Then** 系统正常保存该行程，不因选填项缺失而拒绝

#### Scenario: 必填项缺失时拒绝发布

- **Given** 用户处于发布行程表单
- **When** 任一必填项为空时提交
- **Then** 系统拒绝发布并给出可读的校验提示
- **And** 不产生新的行程

#### Scenario: 日期不合法时拒绝发布

- **Given** 用户处于发布行程表单
- **When** 结束日期早于出发日期并提交
- **Then** 系统拒绝发布并提示日期不合法

#### Scenario: 途经点不足两个时拒绝发布

- **Given** 用户处于发布行程表单
- **When** 有效途经点少于两个并提交
- **Then** 系统拒绝发布并提示至少写出两个途经点

#### Scenario: 计划人数越界时拒绝发布

- **Given** 用户处于发布行程表单
- **When** 计划人数小于 2 或大于 12 并提交
- **Then** 系统拒绝发布并提示人数范围

#### Scenario: 预算区间倒置时拒绝发布

- **Given** 用户填写了预算下限与上限
- **When** 下限高于上限并提交
- **Then** 系统拒绝发布并提示预算区间不合法

#### Scenario: 在地图上添加途经点并看到路线

- **Given** 用户处于发布行程表单并已选择目的地城市
- **When** 用户通过搜索候选、地图点选或景点标记加入两个及以上途经点
- **And** 用户点击「生成旅行路线」
- **Then** 编辑器按加入顺序绘制路线，并展示起点、终点、编号标记、总距离与总时长
- **And** 同一地点重复加入不会产生重复途经点

#### Scenario: 途经点顺序可调整

- **Given** 编辑器内已有三个及以上途经点
- **When** 用户拖拽或使用上下按钮调整顺序
- **Then** 路线折线与编号立即按新顺序重排
- **And** 提交后行程详情按同一顺序展示途经点

#### Scenario: 切换出行方式重算路线

- **Given** 编辑器内已有两个及以上途经点且已生成过路线
- **When** 用户在三档出行方式之间切换
- **Then** 系统自动按所选方式重新规划并更新距离与时长，无需再次点击「生成旅行路线」
- **And** 编辑器显示的选项为「自驾 / 骑行 / 公共交通」，不出现「步行」，也不出现探索页的「驾车」措辞
- **And** 行程顺序面板的出行方式标题与所选方式一致

#### Scenario: 公共交通使用目的地城市规划

- **Given** 用户选择的出行方式为「公共交通」
- **When** 系统规划路线
- **Then** 规划请求以目的地城市限定换乘搜索范围
- **And** 规划失败时按降级口径提示，不展示错误的换乘结果

#### Scenario: 路线服务不可用时按顺序直线示意

- **Given** 编辑器内已有两个及以上途经点
- **When** 路线服务不可用或超时
- **Then** 系统按途经点顺序绘制直线并明确标注「示意 / 估算」
- **And** 页面其余部分保持可用，地图不空白

#### Scenario: 降级提示不暴露实现细节

- **Given** 编辑器内已有两个及以上途经点
- **When** 路线服务不可用或超时，界面进入直线示意状态
- **Then** 降级提示只说明「当前为示意路线、距离与时长为估算」以及用户可采取的下一步
- **And** 提示文本不出现后端服务名、端口号、代理或重载等实现细节

#### Scenario: 发布只提交地名与出行方式

- **Given** 用户已在编辑器中排好途经点顺序
- **When** 用户提交发布
- **Then** 请求体只包含按当前顺序排列的途经点名称数组与出行方式
- **And** 不包含坐标、路线几何或新增字段，契约版本不变

#### Scenario: 坐标占位名不得进入发布

- **Given** 用户通过地图点选加入了途经点，其名称仍是「地图选点 {经度}, {纬度}」的占位形式
- **When** 用户提交发布
- **Then** 系统拒绝提交并提示为该途经点填写可读地名
- **And** 不产生新的行程
- **And** 用户改名后可以正常发布

#### Scenario: AI 预填路线进入编辑器后可编辑

- **Given** 用户从 AI 推荐路线或参考行程进入发布表单
- **When** 表单预填途经点
- **Then** 预填的途经点出现在同一个编辑器中并可直接规划
- **And** 用户可继续排序、删除与重新规划后发布

#### Scenario: 途经点超过上限时被拦截

- **Given** 编辑器中已有 8 个途经点
- **When** 用户尝试加入第 9 个地点
- **Then** 系统拒绝新增并提示最多 8 个途经点
- **And** 已有途经点与路线保持不变

#### Scenario: 窄屏与双主题不溢出

- **Given** 用户在 1440 / 1024 / 768 / 390 宽度与浅色 / 深色主题下填写发布表单
- **When** 页面渲染地图与途经点列表
- **Then** 地图、列表与路线信息正常堆叠或换行，不出现横向溢出
- **And** 途经点名称、距离与提示文字保持可读
