# trip-plans 增量规格

## MODIFIED Requirements

### Requirement: 发布可被他人理解的旅行计划

系统 SHALL 允许已进入的演示用户发布一条旅行计划，发布者 MUST 取当前身份；系统 MUST 按下列约束校验：标题必填且 ≤ 40 字、目的地 MUST 是行政区划字典中的二级节点代码 `destination_code`（必须选到市）、出发与结束日期必填且结束不早于出发、有效途经点至少两个、计划人数为整数且 2–12（含发布者本人，即至少 1 位同行者，`capacity = 1` 视为越界）、预算下限不高于上限、兴趣标签最多 5 个；集合区域、预算范围、兴趣标签与补充说明为选填。目的地名称 MUST 由系统按代码生成，MUST NOT 接受调用方传入的名称。校验失败 MUST NOT 产生新行程。

#### Scenario: 填写完整必填项后成功发布
- **Given** 用户处于发布行程表单
- **When** 用户填写全部必填项并提交
- **Then** 系统保存该行程，状态为「招募中」
- **And** 已加入人数计入发布者本人
- **And** 该行程出现在旅行灵感首页

#### Scenario: 选填项可留空
- **Given** 用户处于发布行程表单
- **When** 用户仅填写必填项、留空全部选填项并提交
- **Then** 系统正常保存该行程，不因选填项缺失而拒绝
- **And** 集合区域、预算范围、兴趣标签与补充说明在详情页按未填写处理

#### Scenario: 必填项缺失时拒绝发布
- **Given** 用户处于发布行程表单
- **When** 任一必填项为空时提交
- **Then** 系统拒绝发布并给出可读的校验提示
- **And** 不产生新的行程

#### Scenario: 必填项缺失时逐项给出字段级错误
- **Given** 用户处于发布行程表单
- **When** 用户清空标题、目的地、出发日期、结束日期与途经点后提交
- **Then** 系统拒绝提交且不发出创建请求
- **And** 每个缺失字段各自显示一条字段级错误提示，而不是只显示一条汇总错误

#### Scenario: 日期不合法时拒绝发布
- **Given** 用户处于发布行程表单
- **When** 结束日期早于出发日期并提交
- **Then** 系统拒绝发布并在结束日期字段提示日期不合法

#### Scenario: 途经点不足两个时拒绝发布
- **Given** 用户处于发布行程表单
- **When** 有效途经点少于两个并提交
- **Then** 系统拒绝发布并提示至少写出两个途经点

#### Scenario: 计划人数越界时拒绝发布
- **Given** 用户处于发布行程表单
- **When** 计划人数小于 2、大于 12 或不是整数并提交
- **Then** 系统拒绝发布并提示人数范围

#### Scenario: 预算区间倒置时拒绝发布
- **Given** 用户填写了预算下限与上限
- **When** 下限高于上限并提交
- **Then** 系统拒绝发布并提示预算区间不合法

#### Scenario: 后端独立校验发布约束
- **Given** 调用方绕过前端直接请求 `POST /api/trips`
- **When** 请求缺少必填字段、结束日期早于出发、有效途经点少于两个、人数为 1 或 13、预算下限高于上限
- **Then** 系统返回 400 `INVALID_INPUT`
- **And** 数据中不产生新的行程

#### Scenario: 目的地代码非法时拒绝发布
- **Given** 调用方绕过前端直接请求 `POST /api/trips`
- **When** 请求携带不存在、非二级或格式错误的 `destination_code`
- **Then** 系统返回 400 `INVALID_INPUT`
- **And** 数据中不产生新的行程

#### Scenario: 发布成功后跳转详情页
- **Given** 用户提交了一条合法的旅行计划
- **When** 系统保存成功
- **Then** 页面跳转到该行程的详情地址 `#/trips/{id}`
- **And** 详情页标题与该次填写的一致

#### Scenario: 首页立即可见新发布的行程
- **Given** 用户刚发布了一条行程
- **When** 用户回到旅行灵感首页
- **Then** 该行程出现在默认的「招募中的行程」列表或按目的地筛选后的结果中
- **And** 状态为「招募中」

#### Scenario: 发布者身份取自当前身份
- **Given** 用户以某个演示身份进入系统
- **When** 用户发布一条行程并查看详情
- **Then** 该行程的发布者是当前身份
- **And** 当前同行者列表包含发布者本人
- **And** 详情页对发布者本人展示「这是你发布的行程」

#### Scenario: 发布的数据在重启后仍在
- **Given** 用户成功发布了一条行程
- **When** 后端进程重启后再次查询该行程
- **Then** 系统仍返回该行程的完整字段

## ADDED Requirements

### Requirement: 发布表单的默认值与地图上下文

系统 SHALL 在打开发布表单时把出发日期与结束日期预填为当天（本地日期），用户可修改且既有校验不变；途经点地图 MUST 在未选目的地时不渲染，选定目的地后 MUST 只展示该市范围与该市的候选地点；表单控件 MUST 撑满字段宽度，字段 MUST 按「基本信息 / 路线 / 补充信息」分组且相邻字段间距一致。

#### Scenario: 日期默认今天
- **Given** 用户打开发布行程表单
- **When** 表单渲染完成
- **Then** 出发日期与结束日期都显示当天日期
- **And** 用户改动日期后按改动后的值校验

#### Scenario: 目的地可点选
- **Given** 用户打开发布行程表单
- **When** 用户点击目的地字段
- **Then** 省 / 市候选面板出现在可视区域内
- **And** 用户可依次选到「广东省 / 珠海」并在字段中看到已选值

#### Scenario: 未选目的地时不展示途经点地图
- **Given** 用户尚未选择目的地
- **When** 用户查看途经点区域
- **Then** 页面不渲染地图
- **And** 显示一句「先选目的地再点选途经点」的引导

#### Scenario: 选定目的地后地图聚焦该市
- **Given** 用户已选择「广东省 / 珠海」
- **When** 用户查看途经点区域
- **Then** 地图出现并只显示该市范围
- **And** 候选点只包含该市的地点
- **And** 地图保持地理比例，不被横向拉伸

#### Scenario: 表单分组与间距一致
- **Given** 用户查看发布行程表单
- **When** 页面渲染完成
- **Then** 字段按「基本信息 / 路线 / 补充信息」分组
- **And** 同组控件宽度一致，相邻字段间距一致
