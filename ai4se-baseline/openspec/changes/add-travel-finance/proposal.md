# 变更提案：add-travel-finance

- **需求来源：** 发起人 2026-11-17 原始诉求「i want new feature: able to buy insurance for accident / death / stomachache during travel from insurance company; able to loan small amount of money for travel support from bank; we charge 5% for service fee」｜ **需求条目：** `requirement-workspace/requirements/REQ-028-travel-finance.md`
- **能力：** `travel-finance`（ADDED）；只读依赖 `trip-plans` / `trip-companions`；`user-auth` 仅作注册集成点；`user-credit` 仅作账本范式参照
- **规模：** M（4 张表 + 1 次迁移 + 演示钱包 / 账本 + 第三方保险入口与状态回写 + 借款与还款 + 2 个新页面 + 3 处入口；无管理端）
- **规则：** `@rule:api-contract`、`@rule:java-patterns`、`@rule:web-coding-style`、`@rule:security-baseline`、`@rule:tdd-cycle`、`@rule:prototype-ui-alignment`、`@rule:sdd-artifacts`

## 问题

RouteME 现在有账号、资料、行程、同行申请、聊天、体验、举报与信用分，但没有任何「钱」的概念：`app_users` 只有身份与资料列，`user_credit_account` 只是 0–100 的信用评分，行程预算 `budget_*_cents` 只是展示字段。发起人要在旅行场景里同时提供两类金融服务——出发前的旅行保险入口，以及旅途中的小额周转金——并对借款按 5% 收服务费。当前缺少三块基础：

- 没有钱包与账本，无法验证「借得到 / 还得起 / 5% 真被扣」，也无法对账；
- 没有保险入口，同行者不知道本次行程可以在哪里投保、保障是否已生效；
- 没有借款、到期与还款模型，周转金额无法闭环；
- 没有资格边界，非同行者或已结束行程仍可能调用写接口。

保险部分**不由 RouteME 承保或定价**：RouteME 不是保险机构，产品设计、核保、保费、保单、理赔与免责条款都由第三方保险服务提供方负责。RouteME 只做两件事：按行程上下文把用户送到第三方的投保入口，并在第三方确认后回写「本次行程是否已投保 / 保障中 / 已结束」，同时展示提供方名称与保单、理赔、紧急求助入口。因此本变更不保存身份证号、银行卡号、保单号等投保敏感信息，也不在 RouteME 内计算保费或保障范围。

本变更只做这条链的**第一段垂直切片**：演示钱包 → 第三方保险入口与状态回写 / 借小额 → 收 5% → 还款与到期展示。理赔、退保、罚息、征信、真实机构 API 对接与管理后台**不在本变更**。

## 范围

**In scope**

- `travel-finance`（ADDED）：演示钱包与 append-only 账本、第三方保险入口与状态回写、借款与手动还款、借款 5% 服务费、行程资格、账号状态边界、整数分精度与幂等、数据隔离。
- 数据：新增 `user_wallet`、`wallet_ledger`、`insurance_policy`、`travel_loan`；新增 1 次迁移（建表 + 回填全部既有账号 1,000,000 分）；**不改** `app_users` 与信用表。
- 注册集成：`AuthServiceImpl.register` 在同一事务内初始化钱包；失败分支不落钱包。
- 保险（第三方模式）：
  - RouteMe **不**设计产品、不计算保费、不承保、不参与理赔；第三方提供方的名称与保单 / 理赔 / 紧急求助地址由配置 `routeme.insurance.*` 提供，默认值为演示占位。
  - `POST /trips/{tripId}/insurance/purchase` 只做资格校验并返回第三方投保地址（附 `trip_id`）；不扣款、不写保单、不产生钱包流水。
  - `POST /trips/{tripId}/insurance/confirm` 供第三方确认后回写：保障期取行程出发日与结束日、状态写 `ACTIVE`；同一用户同一行程幂等，只保留 1 条记录。
  - 状态 `NOT_PURCHASED` / `ACTIVE` / `EXPIRED`；`EXPIRED` 在保障结束日之后由读取时刻只读派生，不迁移、不删除记录。
  - 保障页展示目的地、出发 / 结束日期、同行人数、提供方名称、保障类别与保单 / 理赔 / 紧急求助入口；提供方条款优先。
  - **不保存**身份证号、银行卡号、保单号、保费金额等敏感或定价信息。
- 借款：本金 100–2,000 元整；期限 7 / 14 / 30 天；即时通过；5% 从本金扣除、发放净额；应还 = 本金；0 利息；每人最多 1 笔 `ACTIVE`；手动全额还款；逾期按读取时刻派生、无罚息。
- 资格：行程发布者 + 该行程 `ACCEPTED` 同行者；行程 `recruiting` / `full` / `ongoing`；打开投保入口 / 借款要求账号 `ACTIVE`，还款不受 `SUSPENDED` / `BANNED` 阻断。保险始终可跳过，**不是**加入行程的条件。
- 页面与入口：行程详情「旅行安全保障」区块（含实时状态）；新增行程维度「旅行保障」页（`#/trips/{tripId}/finance`）与账号聚合页（`#/finance`）；账号菜单与侧边栏「我的旅行」下方新增入口。
- 契约：`openapi.yaml` 升次版本 + 钱包 / 第三方保险 / 借款端点与 schema；同步后端契约测试与前端类型。
- 故事与登记：`stories.md` / `stories/add-travel-finance.story.md` / `registry.md` / `handoff.md` 登记 REQ-028 → `add-travel-finance`。

**Out of scope**

- 接入真实保险机构的投保 / 核保 / 出单 API、回调验签、对账文件；RouteME 不成为保险中介或代理。
- 保险产品设计、保费与保额计算、免责条款正文、核保规则、保单批改、退保、理赔审核与给付。
- 真实银行 / 支付网关 / 银行卡绑定 / KYC / 征信 / 真实放款（D9）。
- 借款展期、分期、提前结清优惠、逾期罚息、催收、征信上报、信用分加减。
- 钱包充值 / 提现 / 转账 / 多币种 / 汇率；任何形式的手工调账。
- 管理后台金融订单、风控后台、财务报表、发票（D10）。
- 通知 / 推送 / 邮件 / 短信。
- 改变行程状态机、申请规则、聊天权限、信用分规则。
- 担保人、共同借款、企业账户、未成年人限额与风控。

## 决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 资金形态（D1） | 演示钱包，每用户 1 个余额，初始 10,000 元 | 没有余额就无法验证「借得到 / 还得起」，也无法证明 5% 真被扣；demo 项目不接真实支付 |
| 服务费（D2） | 仅借款从本金扣 5%、发放净额；保险不向用户收平台费 | 保险由第三方定价与收费，RouteME 再加一层费用会变成变相加价且无依据 |
| 借款规则（D3） | 100–2,000 元整、7 / 14 / 30 天、即时通过、0 利息、每人 1 笔进行中、手动还款 | 「small amount」需要可判定上下界；单笔进行中避免演示出现多债叠加 |
| 保险模式（D4） | 第三方入口 + 状态回写，不做站内商品与保单定价 | RouteME 不承保、不设计产品、不计算保费；合规边界清晰，第三方条款优先 |
| 保险数据（D11） | 每 (user, trip) 至多 1 条，含提供方、保障起止日、状态、确认时刻 | 展示「本次行程是否已投保」所需的最小信息；不保存保单号 / 证件 / 银行卡等敏感数据 |
| 保障期（D12） | 固定取行程出发日 ~ 结束日 | 与旅行场景对齐；不引入客户端可传的日期或按日计价 |
| 资格（D5） | 发布者 + `ACCEPTED` 同行者；行程 `recruiting` / `full` / `ongoing` | 服务是「旅行支持」而非无场景现金贷；已完成 / 已取消不再产生新交易；保险可跳过，不阻断同行 |
| 入口（D6） | 行程详情 + 账号菜单 + 侧边栏「我的旅行」下方；另有行程维度页与账号聚合页 | 原话「during travel」以行程为上下文；账号侧负责「我投过什么 / 借过什么」 |
| 命名（D7） | change `add-travel-finance`；capability `travel-finance` | 保险与借款共用钱包、账本、资格与页面；拆两个 change 会复制核心逻辑 |
| 金额口径（D8） | 借款金额整数分（`*_cents`），CNY；只接受整元；保险不出现金额字段 | 避免浮点误差与四舍五入争议；保险金额由第三方决定，RouteMe 不持有 |
| 外部对接（D9） | 配置驱动：`routeme.insurance.*` 提供名称与入口，默认 `example.com` 演示地址；不做真实 API | demo 项目没有外部凭据与合规链路；配置化让接入真实提供方时无需改代码 |
| 明确不做（D10） | 理赔 / 退保 / 罚息 / 分期 / 提现充值 / 发票 / 管理后台金融视图 / 通知 / 信用分影响 | 第一切片只验证「入口可达、状态可对、借得到、费收得到」 |
| 钱包归属 | 新建 `user_wallet`，不复用 `user_credit_account` | 信用分是只读评分，钱包是可扣款余额；混表会让信用分获得支付语义，破坏既有只读约束 |
| 账本幂等 | 流水 append-only + 保险唯一（用户 + 行程）+ 借款部分唯一（用户 + `ACTIVE`）+ 还款状态迁移 | 双击 / 重试不得二次扣款或产生第二条记录；数据库约束兜底比服务层「先查后写」可靠 |
| 还款与账号状态 | 还款不因 `SUSPENDED` / `BANNED` 阻断 | 债务必须可结清；借款仍要求 `ACTIVE` |
| 逾期口径 | 读取时派生「已逾期」，不落独立状态、不罚息、不自动扣款 | 避免定时任务与状态漂移；第一切片不引入惩罚性规则 |
| 契约 / 迁移号 | 0.25.0 + `V30__add_travel_finance.sql` | 合并 `origin/main` 的 0.24.0 + V28 / V29 之后顺延，避免与在途变更撞号 |

## 验收信号

1. 新注册用户与既有账号打开「旅行保障」，钱包余额均为 ¥10,000.00，不出现空值或错误页。
2. 任意一笔借款交易后，钱包余额 = 初始余额 + 入账 − 出账；每笔流水含前后余额、方向、金额、业务类型与关联业务；保险不产生流水。
3. 行程保障页展示目的地、出发 / 结束日期、同行人数、实际提供方名称，以及保单 / 理赔 / 紧急求助入口；提供方免责说明可见。
4. 点「前往第三方购买」只打开第三方地址（带 `trip_id`），余额、保单与流水均无变化。
5. 第三方确认后回写为 `ACTIVE`，保障期为行程出发日 ~ 结束日；重复回写返回同一条记录，不产生第二条。
6. 保障结束日之后读取状态为 `EXPIRED`，记录与保障期仍可查看；未购买时为 `NOT_PURCHASED` 且 `policy` 为 null。
7. RouteMe 的任何响应与表结构都不包含保单号、身份证号、银行卡号或保费金额。
8. 借 1,000 元、14 天：到账 950 元、应还 1,000 元、到期 = 放款 + 14 天；不产生利息或第二笔费用。
9. 已有进行中借款时再次申请被拒绝；还清后可再次申请。
10. 还款扣本金后借款变为「已还清」；逾期只展示「已逾期」，应还金额不变。
11. 非同行者、`completed` / `cancelled` 行程、`SUSPENDED` / `BANNED` 账号的投保入口 / 借款请求均被服务端拒绝；封禁账号仍可还款。
12. 双击或重试同一借款 / 还款 / 状态回写请求，至多生效一次，不产生第二笔进行中借款或第二条记录。
13. 用户只能看到自己的钱包、保险记录与借款。
14. `openspec validate add-travel-finance --strict` 通过；既有行程、申请、聊天、体验、举报、信用分与管理后台不回归。

## 残余风险

| 风险 | 处理 |
|---|---|
| 用户误以为 RouteME 承保或负责理赔 | 页脚固定展示「RouteMe 仅提供入口，不承保也不参与理赔」，并展示实际提供方名称与条款 / 理赔 / 求助入口；验收信号 3 覆盖 |
| 演示环境伪造「已完成投保」 | 确认端点只在演示 / 联调配置下由前端按钮触发；生产接入需替换为第三方回调与验签，已在 Out of scope 与残余风险中登记 |
| 第三方入口地址不可用 | 配置默认指向 `example.com` 演示页；真实地址通过环境变量覆盖，不改代码 |
| 保险状态与第三方实际状态不一致 | RouteMe 只保存第三方确认结果并展示；以提供方条款与系统为准，差异由第三方对账负责 |
| 借款端把 5% 误解为「加到还款额」 | 提案 / 需求 / Delta 三处写死「从发放额扣」；验收信号 8 用净额与应还额锁定 |
| 余额并发双花 | 事务内条件更新 + 账本同事务；服务单测覆盖并发与重试 |
| 封禁用户无法还款导致债务永续 | 还款单独放行；验收信号 11 覆盖 |
| 浮点误差导致费用对不上 | 借款金额全整数分；后端禁止 `double`；前端只格式化 |
| 非同行者直连端点绕过 UI | 服务端资格校验为唯一权威；UI 仅展示 |
| 与在途变更同改契约 / 迁移 | 契约 0.25.0、迁移 V30 已在合并 `origin/main` 后确认；PR 描述记录合并顺序 |
