# 变更提案：add-user-profile

- **需求来源：** 用户故事「作为新用户，我希望完善个人资料……让其他用户在查看我的行程时能够更好地了解我」+ 16 条验收标准 ｜ **需求条目：** `requirement-workspace/requirements/REQ-008-user-profile.md`
- **能力：** `user-profile`（ADDED）、`user-auth`（MODIFIED）
- **规模：** M（新增 1 个页面 + 1 份资料契约 + 3 个资料端点 + 1 次迁移；注册表单收窄；行程 / 体验只改发布者展示入口）
- **规则：** `@rule:package-structure`、`@rule:java-patterns`、`@rule:web-coding-style`、`@rule:api-contract`、`@rule:security-baseline`、`@rule:sdd-artifacts`

## 问题

RouteME 现在能注册、登录、退出，但没有「人」：`app_users` 只有昵称、首字头像、学校、简介与兴趣；注册表单顺手收了学校、简介和兴趣，用户没有地方填生日、性别、城市、专业、职业、MBTI、旅行方式，也没有头像上传。发布者在行程卡和详情页上只是「昵称 + 首字 + 学校字符串」——浏览者无法判断「这个人多大、什么星座、怎么旅行、是不是一个合拍的同行者」。`trip-plans` 里演示账号的「研一 · 地理科学」还把年级和专业塞进一个字段，真实用户要照着输间隔号 `·` 才能获得同样的展示，既难输入也不稳定；不在校的用户也没有合适的身份表达。

产品希望把「账号」和「资料」分开：注册只负责创建账号，资料在一个独立页面上一次性补齐；保存后生成个人主页，其他人在查看发布者时能看到同一份资料。这既是新用户故事（P0，迭代 1，3 点），也要求注册流程不再抢资料的活。

## 范围

**In scope**

- `user-profile`（ADDED）：头像（选填、真实上传）、昵称、生日 → 派生年龄 / 星座、性别、所在城市、学校（选填）、专业（选填）、职业（选填）、MBTI（选填）、旅行兴趣（3–5）、旅行方式（单选）、个人简介（选填）。
- 必填规则：昵称、生日、性别、所在城市、旅行兴趣（≥3）、旅行方式；未完成时不能提交，并逐项 + 汇总提示缺失字段。学校、专业与职业均不参与必填校验。
- 资料完善状态「未完善 → 已完善」由必填字段派生；可跳过，稍后从「我的」补全；未完善时他人看到已有字段 + 「资料尚未完善」提示。
- 个人主页（本人可编辑，他人只读）；行程卡 / 行程详情的发布者入口进入该主页。
- `user-auth`（MODIFIED）：「注册账号」收窄为用户名 / 密码 / 昵称；注册成功进入资料完善页；新账号初始为资料未完善。
- 契约 `openapi.yaml` 升至 0.7.0：新增个人资料 schema 与 3 个端点；注册请求体移除学校 / 简介 / 兴趣。
- 迁移：`app_users` 增加头像、生日、性别、城市、专业、职业、MBTI、旅行方式列；不新增表。

**Out of scope**

- 手机号 / 邮箱验证、实名认证、第三方登录、改密码 / 找回密码、账号注销。
- 头像裁剪编辑器、相册、背景图、动态、关注、私信、资料可见性开关。
- 旅行兴趣词表与行程标签匹配算法的统一（P3 设计项）。
- 演示身份资料编辑、演示账号数量与进入 / 切换行为。
- 行程、申请、聊天、体验的业务规则变更；只改发布者展示入口。
- 新增独立导航项（「完善资料」入口挂在「我的」与个人主页上）。

## 决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 能力拆分 | 新增 `user-profile`，并 MODIFIED `user-auth` | 资料是新业务概念；注册收窄改变既有「注册账号」规则，无法只靠 ADDED 表达 |
| 头像 | 真实上传图片，但**选填**（用户裁决 D1） | 满足「上传头像」的原意，同时不因图片存储故障挡住资料保存；无头像回退昵称首字 |
| 学校 / 专业 / 职业 | 学校、专业、职业三个独立输入；学校、专业与职业均为选填（用户裁决 D2 / D6） | 用户不必输入间隔号 `·`；学校选填后非学生不再被挡住；职业与学校可同时填写；演示账号保留旧文案 |
| 注册表单 | 瘦身为用户名 / 密码 / 昵称（用户裁决 D3） | 避免同一字段填两次；注册只承担「创建账号」 |
| 完善页门禁 | 可跳过，可从「我的」补全（用户裁决 D4） | 不阻断浏览、发布等既有路径；「资料未完善」允许长期存在并降级展示 |
| 旅行方式 | 单选（用户裁决 D5） | AC 用「如」列举四项，语义是「我是哪一类旅行者」；多选会让匹配与展示失去焦点 |
| 兴趣上限 | 3–5 个（用户裁决 D5） | 沿用既有选择器的 5 个上限与匹配计算假设，只新增下限 |
| 年龄 / 星座 | 服务端按当前日期计算，只读返回 | 避免前端时区 / 年龄口径分叉；生日原文不对外返回 |
| 完善状态 | 由必填字段派生，不落库 | 避免状态列与字段更新不同步；对外以布尔值暴露 |
| 个人主页 | 本人编辑态、他人只读，同一路由 | 一个页面承载「完善 / 查看 / 编辑」，避免再拆一条故事 |
| 演示身份 | 只读，不展示编辑入口 | 演示账户是评审样本，不应被编辑污染 |
| 兴趣词表 | 预设至少覆盖 AC 的 10 个，允许自定义 | 不阻塞本故事；与行程标签的别名归一化留到 P3，避免扩成匹配改造 |

## 验收信号

1. 注册只填用户名 / 密码 / 昵称即可成功；注册成功后落在资料完善页，页面不要求再次输入用户名或密码。
2. 必填项缺任一项时提交被阻止，字段级错误与「还有 N 项未完成」汇总同时出现，且缺失字段名称可读。
3. 填写生日后，资料与个人主页展示由服务端计算的周岁年龄与星座；他人资料响应中没有完整生日。
4. 学校、专业与职业分别录入；学校与专业拼为「学校 · 专业」，职业单独展示；只填职业或只填学校时只展示已填内容，不出现空行或占位符。
5. 兴趣少于 3 个不能提交，超过 5 个不能继续添加；自定义标签取消后保留可复选。
6. 无头像时回退昵称首字；上传合法图片后个人主页与发布者入口同步显示新头像。
7. 保存成功后进入本人个人主页；其他用户从行程卡 / 详情发布者入口打开同一页面，且没有编辑入口。
8. 跳过完善页仍可使用既有功能；从「我的」补全后状态变为已完善。
9. 演示身份没有「完善 / 编辑资料」入口，直接调用资料保存接口返回 403。
10. `openspec validate add-user-profile --strict` 通过；既有注册、登录、会话恢复、退出、行程、申请、聊天、体验不回归。

## 残余风险

| 风险 | 处理 |
|---|---|
| 双 capability（`user-profile` ADDED + `user-auth` MODIFIED）违反「一个 change 一个 capability」的默认口径 | 与 REQ-005 同口径：注册收窄是资料状态迁移的起点，拆开会让「注册 → 完善 → 主页」垂直切片断成两半；归档前需 SA 追认例外 |
| 兴趣词表（自然风景 / 文化历史 / 看展）与行程标签（自然 / 历史 / 展览）不完全一致，会影响匹配理由 | 本 change 不改匹配算法；P3 设计统一词表 / 别名时再处理，避免本故事扩成匹配改造 |
| 头像文件落盘带来静态资源目录、清理与安全边界 | 只接受 JPEG / PNG / WebP 且 ≤2 MB；文件名由服务端生成；P3 设计确认目录与访问路径 |
| 注册请求体收窄会破坏既有前端 / 测试 / 演示脚本 | 契约升至 0.7.0 并在 P4 同步更新 `api.test.ts`、`authForm.test.ts` 与 E2E；旧字段忽略而非报错（兼容期） |
| 完善状态派生与字段更新可能不一致 | 派生函数与资料响应共用同一实现；测试覆盖「部分必填」「演示账号」「旧账号」 |
| 个人主页暴露过多资料 | 生日不公开；只公开昵称、头像、年龄、星座、性别、城市、学校、专业、职业、MBTI、兴趣、旅行方式与简介；访客不可见 |
| 注册用户可能在完善前就发布行程，他人查看时资料为空 | 未完善资料走降级展示（昵称 / 首字 / 已填的学校或职业 + 提示）；发布不新增门禁 |
| 学校改为选填后，行程卡 / 详情原有的「学校」一行可能为空 | 发布者摘要按「学校 · 专业 → 职业 → 城市」顺序取第一个可用值；全空时只显示昵称与头像，不留空行 |
