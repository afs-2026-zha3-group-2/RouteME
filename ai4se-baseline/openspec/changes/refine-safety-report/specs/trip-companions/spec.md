# trip-companions 增量规格（refine-safety-report）

## MODIFIED Requirements

### Requirement: 我的旅行聚合与最低安全能力

系统 SHALL 提供「我的旅行」分区视图（我发布的、我申请的、已匹配的、已完成的），并在有待处理申请时给出可点击提醒。系统 MUST 在行程详情页以三条文本列表、在聊天页以一行文本展示安全事实——公共场所集合（含本行程集合区域）、把行程告知亲友并约定报平安、平台不公开电话 / 证件 / 精确住址并拒绝转账或索要证件——并提供以行程或用户为对象的举报入口；提交后 MUST 返回「已收到，我们会处理」的明确回执。本人发布的行程 MUST NOT 出现以该行程为对象的举报入口，但安全提示照常展示。提示与回执 MUST NOT 仅靠颜色或图标表达；系统 MUST NOT 采集或展示电话、证件与精确住址；MVP 不要求举报处置闭环，且不向被举报方透露举报人身份。

#### Scenario: 分区展示我的旅行
- **Given** 用户既发布过行程也提交过申请
- **When** 用户进入我的旅行
- **Then** 系统按我发布的、我申请的、已匹配的、已完成的四个分区展示
- **And** 每个条目可跳转到对应行程或申请

#### Scenario: 待处理申请提醒
- **Given** 用户发布的行程存在待处理申请
- **When** 用户进入我的旅行
- **Then** 系统显示待处理数量与可点击入口

#### Scenario: 安全提示常驻
- **Given** 用户打开一条行程的详情页（无论是否为本人发布）
- **When** 页面加载完成
- **Then** 安全区以文本列表展示三条事实：首次见面请选公共场所（含「本行程集合区域：{集合区域}」）、把目的地 / 日期 / 同行人昵称告知亲友并约定报平安时间、平台不公开电话 / 证件 / 精确住址且任何转账或索要证件的请求都应拒绝
- **And** 集合区域为空时显示「尚未填写，出发前请在聊天中确认」
- **And** 提示不只靠颜色或图标表达，列表文本可被读屏读取

#### Scenario: 聊天页展示安全提示
- **Given** 已匹配用户进入与该行程的聊天页（包含行程已结束的只读聊天）
- **When** 页面加载完成
- **Then** 消息区上方以一行文本展示：公共场所集合 + 集合区域（为空时显示「待确认」）+ 不要转账或提供证件信息
- **And** 提示不只靠颜色或图标表达

#### Scenario: 举报入口与举报对象
- **Given** 用户正在查看他人发布的行程详情，或正在聊天页与对方沟通
- **When** 用户查看安全区并打开举报弹窗
- **Then** 详情页提供「举报这条行程」，聊天页提供「举报这位用户」
- **And** 弹窗标明举报对象（行程标题或对方昵称）、四类原因（骚扰或不当言行 / 虚假信息 / 安全风险 / 其他）与选填说明（200 字以内）
- **And** 弹窗展示「我们不会向对方透露你的身份」与「如果你正处于危险中，请先联系当地警方或学校保卫处。平台举报不能替代紧急求助。」

#### Scenario: 本人行程不出现举报入口
- **Given** 用户打开自己发布的行程详情
- **When** 用户查看安全区
- **Then** 三条安全提示照常展示
- **And** 不出现「举报这条行程」入口

#### Scenario: 提交举报并收到回执
- **Given** 用户在举报弹窗中已选定原因（可填写不超过 200 字的说明）
- **When** 用户提交举报
- **Then** 系统记录该举报并返回已接收
- **And** 弹窗进入回执态并展示「已收到，我们会处理」
- **And** 关闭弹窗只结束回执展示，不改变行程、申请或聊天状态，MVP 不要求处置闭环，也不向被举报方透露举报人身份

#### Scenario: 提交失败可读且可重试
- **Given** 网络或服务端错误
- **When** 用户提交举报
- **Then** 弹窗展示可读的失败提示，并保留已选原因与已填说明
- **And** 重试成功后仍进入回执态，且不出现重复回执或多条可见记录

#### Scenario: 安全区不展示隐私字段
- **Given** 用户阅读详情页安全区、聊天页提示或举报弹窗
- **When** 阅读全部文案
- **Then** 不出现电话、证件、精确住址等隐私字段的采集或展示
- **And** 提示只要求用户不对外公开这些信息
