# notifications 增量规格（add-realtime-notifications）

## ADDED Requirements

### Requirement: 申请与裁决产生持久化通知

当一次申请创建成功时，系统 MUST 为行程发布者创建恰好一条 `application_received` 通知；当一条 pending 申请被接受或拒绝时，系统 MUST 为申请者创建恰好一条 `application_accepted` 或 `application_rejected` 通知。每条通知 MUST 记录收件人、动作人、行程、关联申请与创建时间。既有状态机拒绝的请求（重复申请、申请非 pending、行程未开放或已满）MUST NOT 产生任何通知。通知的写入 MUST NOT 改变申请或裁决的成功条件：通知写入失败时，系统 MUST 记录失败并仍向调用方返回既有的成功结果。

#### Scenario: 申请到达时为发布者创建一条通知
- **Given** 用户 B 申请用户 A 发布的、仍开放的行程
- **When** 申请创建成功
- **Then** A 恰好有 1 条 `application_received` 通知
- **And** 该通知的动作人为 B、关联该行程与该申请、创建时间为申请成功的时间

#### Scenario: 接受时为申请者创建一条通知
- **Given** B 对该行程的申请处于 pending
- **When** A 接受该申请
- **Then** B 恰好有 1 条 `application_accepted` 通知
- **And** 该通知的动作人为 A 并关联该行程

#### Scenario: 拒绝时为申请者创建一条通知
- **Given** B 对该行程的申请处于 pending
- **When** A 拒绝该申请
- **Then** B 恰好有 1 条 `application_rejected` 通知
- **And** 该通知的动作人为 A 并关联该行程

#### Scenario: 被既有规则拒绝的请求不产生通知
- **Given** 请求会触发重复申请、申请非 pending、行程未开放或行程已满中的任一条
- **When** 该请求被拒绝
- **Then** 不创建任何通知
- **And** 收件人的未读计数不变

#### Scenario: 通知失败不回滚裁决
- **Given** 通知写入或推送发生失败
- **When** A 接受 B 的申请
- **Then** 申请状态仍变为 `accepted`
- **And** 调用方仍收到成功结果
- **And** 失败被记录，供排障使用

### Requirement: 聊天消息产生通知

当一条聊天消息落库成功时，系统 MUST 为接收方创建恰好一条 `message` 通知，并 MUST 在该通知中携带该会话的定位信息（行程 id 与发送方 id）与该消息 id。发送方与接收方为同一用户的消息 MUST NOT 产生通知。

#### Scenario: 每条消息一条通知
- **Given** A 与 B 存在可访问的会话
- **When** A 向 B 发送一条消息并落库成功
- **Then** B 恰好有 1 条 `message` 通知
- **And** 该通知关联该行程、该发送方与该消息

#### Scenario: 自己给自己发消息不产生通知
- **Given** 用户在自己与自己之间发送一条消息
- **When** 消息落库成功
- **Then** 不创建任何 `message` 通知
- **And** 该用户的未读计数不变

### Requirement: 未读计数与通知列表

系统 MUST 提供按用户读取的未读计数与通知列表。未读计数 MUST 由未读通知记录（已读时间为空）派生，并 MUST 拆分为总数、申请类、消息类三项。计数 MUST 在页面刷新或推送通道重连后返回与持久化状态一致的值。列表 MUST 按创建时间倒序返回该用户最新 50 条通知，每条 MUST 包含动作人摘要、行程 id 与标题、可读文案、创建时间与是否已读。

#### Scenario: 刷新或重连后计数不变
- **Given** 用户有 N 条未读通知
- **When** 页面刷新或推送通道重连后重新读取
- **Then** 未读总数仍为 N

#### Scenario: 计数按类型拆分
- **Given** 用户有 2 条未读申请类通知与 3 条未读消息类通知
- **When** 读取未读计数
- **Then** 总数为 5、申请类为 2、消息类为 3

#### Scenario: 列表按时间倒序且最多 50 条
- **Given** 用户存在多于 50 条通知
- **When** 读取通知列表
- **Then** 返回最新的 50 条
- **And** 条目按创建时间从新到旧排列

#### Scenario: 列表条目上下文完整
- **Given** 列表中任意一条通知
- **Then** 它包含动作人摘要、行程 id 与标题、可读文案、创建时间与是否已读

### Requirement: 实时投递

系统 MUST 通过按用户的服务器推送通道，在通知创建后 3 秒内把该通知推送给收件人已打开的会话，且 MUST NOT 把它推送给其他用户。连接 MUST 由周期心跳保持，并 MUST 在客户端断开后释放。每次连接建立后，客户端 MUST 重新读取 REST 列表与未读计数，使漏推与重连收敛到持久化状态且不产生重复条目。推送通道不可用时 MUST NOT 影响应用其它功能，最后一次已知计数 MUST 保持可见。

#### Scenario: 只推送给收件人
- **Given** A 与 B 都打开了推送通道
- **When** 一个只与 A 有关的通知被创建
- **Then** 只有 A 的通道收到该通知
- **And** B 的通道不收到与该通知相关的任何事件

#### Scenario: 通知在 3 秒内到达已连接的收件人
- **Given** 收件人的推送通道已连接
- **When** 通知被创建
- **Then** 客户端在 3 秒内反映该通知
- **And** 无需刷新页面

#### Scenario: 重连对账不丢不重
- **Given** 推送通道断开期间发生过通知
- **When** 客户端重连
- **Then** 它重新读取列表与计数
- **And** 计数与持久化状态一致且没有重复条目

#### Scenario: 空闲连接由心跳保持并在断开后释放
- **Given** 一条连接长时间空闲
- **When** 心跳周期到达
- **Then** 服务端通过该连接发送心跳事件
- **And** 客户端断开后该连接被释放

#### Scenario: 推送通道失败不影响其它功能
- **Given** 推送通道无法建立或中途失败
- **When** 用户继续使用应用
- **Then** 其它功能照常可用
- **And** 最后一次已知的未读计数仍显示
- **And** 不出现阻塞式错误弹窗

### Requirement: 标读范围

系统 MUST 支持把单条通知、某个会话的全部消息类通知、或全部通知标记为已读。标读 MUST 幂等：对已读通知再次标读 MUST NOT 改变任何计数。标读 MUST 只影响发起标读的用户自己的通知。用户打开某个会话时，系统 MUST 只把该会话（行程 id 与对方用户 id 共同限定）的消息类通知标记为已读，其它会话的消息类通知与所有申请类通知 MUST 保持未读。

#### Scenario: 读一条只减一
- **Given** 用户有若干未读通知
- **When** 该用户打开其中一条
- **Then** 该条变为已读
- **And** 未读总数恰好减 1

#### Scenario: 全部已读归零
- **Given** 用户有若干未读通知
- **When** 该用户选择「全部已读」
- **Then** 未读总数为 0
- **And** 列表中每一条都是已读

#### Scenario: 打开会话只清该会话的消息
- **Given** 用户有两个会话各有未读消息，且有未读申请类通知
- **When** 该用户打开其中一个会话
- **Then** 只有该会话的消息类通知变为已读
- **And** 另一个会话的消息类通知与所有申请类通知仍未读

#### Scenario: 重复标读不改变计数
- **Given** 一条通知已经是已读
- **When** 再次对它执行标读
- **Then** 未读总数、申请类与消息类计数都不变

#### Scenario: 标读按用户隔离
- **Given** A 与 B 各有未读通知
- **When** A 把自己的通知标记为已读
- **Then** B 的未读计数不变

### Requirement: 壳层指示与直达

当存在未读通知时，全局壳层 MUST 以数字显示未读数量，MUST NOT 仅以颜色表达；顶栏 MUST 提供一个显示该数字的入口与可展开的通知面板。聊天入口（侧栏以及视口 ≤900 px 时的移动 tab）MUST 显示消息类未读数，会话列表 MUST 显示每个会话的未读消息数。数量为 0 时 MUST NOT 显示徽标。面板 MUST 列出最新通知的动作人、文案、时间与未读标记，并 MUST 提供「全部已读」。激活一条通知 MUST 打开其目标（申请类 → 对应行程页；消息类 → 对应会话）并把该条标记为已读。用户正在查看的会话收到新消息时，消息 MUST 无需手动刷新即出现，且该会话的未读数 MUST 保持 0。视口 ≤900 px 时，聊天 tab MUST 显示同样的消息数，顶栏入口 MUST 仍可触达。

#### Scenario: 数字徽标随未读数出现与消失
- **Given** 用户有未读通知
- **Then** 顶栏入口以数字显示未读总数
- **And** 聊天入口显示消息类未读数
- **And** 会话列表中每个有未读消息的会话显示其未读数
- **When** 用户把所有通知标记为已读
- **Then** 顶栏入口与聊天入口的徽标都消失
- **And** 不保留仅有颜色的圆点

#### Scenario: 面板列出最新通知并可全部已读
- **Given** 用户打开顶栏入口
- **Then** 面板列出最新通知，每条含动作人、文案、时间与未读标记
- **And** 面板提供「全部已读」
- **And** 执行「全部已读」后徽标消失

#### Scenario: 激活通知直达目标并标读
- **Given** 一条未读通知
- **When** 用户激活它
- **Then** 申请类通知打开对应行程页
- **And** 消息类通知打开对应会话
- **And** 该条通知变为已读

#### Scenario: 当前会话的消息即时出现且不累计未读
- **Given** 用户正在查看某个会话
- **When** 该会话收到一条新消息
- **Then** 消息无需手动刷新即出现
- **And** 该会话的未读数保持 0
- **And** 申请类通知的未读数不受影响

#### Scenario: 窄屏下计数口径一致
- **Given** 视口宽度 ≤900 px 且用户有未读消息
- **Then** 移动 tab 的聊天入口显示与侧栏相同的消息数
- **And** 顶栏入口仍可触达
- **And** 数字仍以文本形式呈现
