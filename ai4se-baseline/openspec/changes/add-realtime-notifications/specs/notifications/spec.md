# notifications 增量规格（add-realtime-notifications）

## ADDED Requirements

### Requirement: 通知记录、类型与生命周期

当八类业务事件（`TRIP` / `APPLICATION` / `CHAT` / `CREDIT` / `REPORT` / `ACCOUNT` / `SERVICE` / `SYSTEM`）中任一事件成功发生时，系统 MUST 为目标收件人创建一条持久化通知。每条通知 MUST 记录类型、事件、标题、正文、优先级、创建时间、已读时间、动作人（可空）与关联业务对象。通知 MUST 有两种状态 `UNREAD` / `READ`，且 MUST 由已读时间是否为空派生，MUST NOT 另存一份可与已读时间矛盾的独立状态。同一业务事件对同一收件人 MUST 只产生一条通知：以收件人与该事件的去重标识共同唯一，重复触发、重试或重复读取 MUST NOT 增加条目或未读计数。业务状态变化 MUST NOT 删除或改写既有通知，标读 MUST NOT 改变任何业务状态。

#### Scenario: S30-1 八类与两态
- **Given** 任意一条通知记录
- **Then** 其类型取值为八个大写枚举之一
- **And** 其事件为表示具体业务事件的 snake_case 名称
- **And** 其状态为 `UNREAD` 或 `READ`，且与已读时间一致

#### Scenario: S30-2 字段完整
- **Given** 通知列表中的任意一条
- **Then** 它带类型、事件、标题、正文、优先级、状态、创建时间、已读时间、动作人摘要（可为空）与关联对象标识
- **And** 它带一个目标描述与「关联对象当前是否可访问」标记

#### Scenario: S30-3 同一事件只一行
- **Given** 同一业务事件被重复触发
- **When** 系统尝试再次写入通知
- **Then** 同一收件人对同一事件仍只有 1 条记录
- **And** 未读总数不因重复触发而增加

#### Scenario: S30-4 只增不删
- **Given** 一条通知已经存在
- **When** 行程取消或结束、举报处理完成、账号恢复、或用户把它标为已读
- **Then** 该通知仍然存在且正文不变
- **And** 相关业务状态不受标读影响

### Requirement: 行程生命周期事件

当行程因接受申请而达到容量时，系统 MUST 为除接受动作发起人之外的每位已接受参与者创建一条 `TRIP` 通知。当行程进入 `ONGOING` 且参与者读取行程详情时，系统 MUST 为发布者与已接受同行者各创建一条 `TRIP` 通知与一条 `SYSTEM` 安全提醒通知，且重复读取 MUST NOT 重复生成。当行程被取消时，系统 MUST 为每位已接受同行者创建一条带取消原因的 `TRIP` 通知。当行程完成时，系统 MUST 为每位已接受同行者创建一条 `TRIP` 通知。

#### Scenario: S30-5 行程满员
- **Given** 行程容量为 2 且已有 1 名已接受同行者
- **When** 发布者接受唯一一名待处理申请
- **Then** 该同行者收到恰好 1 条「行程已满员」的 `TRIP` 通知
- **And** 发起该接受动作的发布者不因自己的动作收到同类通知

#### Scenario: S30-6 行程开始与安全提醒
- **Given** 行程已到开始时间且状态为 `ONGOING`
- **When** 发布者打开该行程详情
- **Then** 发布者与每位已接受同行者各得到 1 条「行程已开始」通知与 1 条安全提醒通知
- **And** 再次打开该详情不产生新的同类通知

#### Scenario: S30-7 行程取消
- **Given** 行程有已接受同行者与待处理申请
- **When** 发布者取消该行程
- **Then** 每位已接受同行者收到 1 条带取消原因的 `TRIP` 通知
- **And** 通知正文说明行程已取消及原因

#### Scenario: S30-8 行程结束
- **Given** 行程有已接受同行者
- **When** 行程到达结束时间并完成
- **Then** 每位已接受同行者收到 1 条「行程已结束」的 `TRIP` 通知
- **And** 该通知的目标为对应行程详情

### Requirement: 申请与裁决事件

当一次申请创建成功时，系统 MUST 为行程发布者创建恰好一条 `APPLICATION` 通知，其目标 MUST 指向该行程的申请处理页。当一条待处理申请被接受或拒绝时，系统 MUST 为申请者创建恰好一条 `APPLICATION` 通知，其目标 MUST 指向对应行程详情。当行程取消导致待处理申请关闭时，系统 MUST 为该申请者创建恰好一条带取消原因的 `APPLICATION` 通知。既有状态机拒绝的请求（重复申请、申请非待处理、行程未开放或已满、行程已取消或已完成）MUST NOT 产生任何通知。通知的写入 MUST NOT 改变申请与裁决的成功条件：通知失败时系统 MUST 记录失败并仍返回既有成功结果。

#### Scenario: S30-9 申请到达
- **Given** B 申请 A 发布的、仍开放的行程
- **When** 申请创建成功
- **Then** A 恰好有 1 条「新的同行申请」通知
- **And** 该通知的动作人为 B、关联该行程与该申请、目标为申请处理页

#### Scenario: S30-10 申请通过
- **Given** B 对该行程的申请处于待处理
- **When** A 接受该申请
- **Then** B 恰好有 1 条「申请已通过」通知
- **And** 该通知的动作人为 A、目标为行程详情

#### Scenario: S30-11 申请被拒
- **Given** B 对该行程的申请处于待处理
- **When** A 拒绝该申请
- **Then** B 恰好有 1 条「申请未通过」通知
- **And** 该通知的动作人为 A、目标为行程详情
- **And** 通知正文不包含拒绝的内部理由码

#### Scenario: S30-12 申请关闭
- **Given** 一条待处理申请所属的行程被取消
- **When** 该申请随之关闭
- **Then** 该申请者恰好有 1 条「申请已关闭」通知
- **And** 通知正文含行程取消原因

### Requirement: 聊天、信用、举报与账号事件

当一条聊天消息落库成功时，系统 MUST 为接收方创建恰好一条 `CHAT` 通知，并携带该会话的定位信息与消息标识；发送方与接收方为同一用户时 MUST NOT 产生通知。当用户信用分发生变化时，系统 MUST 创建一条 `CREDIT` 通知，正文 MUST 说明变化量、原因与变动后分数，且分数低于 60 时优先级 MUST 为高。当用户完成安全学习使分数恢复到阈值以上时，系统 MUST 创建一条说明限制已解除的 `CREDIT` 通知。当举报被提交、进入处理中、处理完成时，系统 MUST 各创建一条 `REPORT` 通知给举报人，正文 MUST 只含举报编号与处理结论。当账号被暂停、封禁或恢复时，系统 MUST 为本人创建 `ACCOUNT` 通知；暂停与封禁通知 MUST 说明受限内容与恢复时间，MUST NOT 包含管理员备注或其他用户的数据。

#### Scenario: S30-13 聊天消息
- **Given** A 与 B 存在可访问的会话
- **When** A 向 B 发送一条消息并落库成功
- **Then** B 恰好有 1 条 `CHAT` 通知
- **And** 该通知关联该行程、该发送方与该消息
- **And** A 不因自己发送的消息收到通知

#### Scenario: S30-14 信用变动
- **Given** 用户的信用分因一次已记账的业务动作发生变化
- **When** 系统创建信用通知
- **Then** 正文含变化量、原因与变动后分数
- **And** 变动后分数低于 60 时该通知标记为重要

#### Scenario: S30-15 信用恢复
- **Given** 用户因低信用处于限制状态
- **When** 该用户完成安全学习使分数恢复到阈值以上
- **Then** 用户收到 1 条「限制已解除」的信用通知
- **And** 该通知标记为重要

#### Scenario: S30-16 举报全流程
- **Given** 用户提交了一条举报
- **When** 举报提交成功、管理员开始处理、管理员处理完成
- **Then** 举报人在三个时点各收到 1 条 `REPORT` 通知
- **And** 每条通知正文只含举报编号与当前处理结论

#### Scenario: S30-17 账号状态
- **Given** 管理员对某用户执行暂停、封禁或恢复
- **When** 操作成功
- **Then** 该用户本人收到 1 条对应状态的 `ACCOUNT` 通知
- **And** 暂停与封禁通知说明受限内容与恢复时间
- **And** 通知不含管理员备注或其他用户的数据

### Requirement: 客服与系统事件

当人工客服接入会话、回复消息或结束会话时，系统 MUST 为用户创建对应的 `SERVICE` 通知，其目标 MUST 指向客服入口。当行程进入 `ONGOING` 时，系统 MUST 为参与者创建安全提醒的 `SYSTEM` 通知，其目标 MUST 指向对应行程详情。当用户资料首次变为完整时，系统 MUST 为该用户创建恰好一条身份认证结果的 `SYSTEM` 通知，其目标 MUST 指向身份资料页，重复补全 MUST NOT 重复生成。

#### Scenario: S30-18 客服会话
- **Given** 用户有一条客服会话
- **When** 人工客服接入、回复消息、结束会话
- **Then** 用户依次收到对应的三条 `SERVICE` 通知
- **And** 每条通知的目标为客服入口

#### Scenario: S30-19 系统安全提醒
- **Given** 行程已进入 `ONGOING`
- **When** 参与者的通知被创建
- **Then** 每位已接受参与者收到 1 条安全提醒的 `SYSTEM` 通知
- **And** 该通知的目标为对应行程详情

#### Scenario: S30-20 身份认证
- **Given** 用户资料此前不完整
- **When** 该用户首次把资料补全到完整
- **Then** 用户恰好收到 1 条身份认证结果的 `SYSTEM` 通知
- **And** 再次修改资料不重复生成
- **And** 该通知的目标为身份资料页

### Requirement: 通知中心与跳转

系统 MUST 提供一个通知中心，展示该用户的通知列表并支持按八类筛选；筛选控件 MUST 显示该类型的未读数，全部类型 MUST 显示未读总数；通知中心 MUST 提供一键「全部已读」。激活一条通知 MUST 把它标为已读，并按其后端下发的目标打开对应页面：`TRIP` → 对应行程详情；`APPLICATION` 中的「申请到达」→ 申请处理页，其余申请事件 → 对应行程详情；`CHAT` → 该会话；`CREDIT` → 信用记录页；`REPORT` → 该举报详情；`ACCOUNT` → 本人的账号与信用状态页；`SERVICE` → 客服入口；`SYSTEM` 中的身份认证 → 身份资料页，安全提醒 → 对应行程详情。关联对象已不可访问时，通知 MUST 保留原有正文，MUST 明确提示「相关内容当前不可查看」，MUST NOT 跳转或报错，且 MUST 仍把该条标为已读。

#### Scenario: S30-21 行程类跳转
- **Given** 一条关联行程仍存在的 `TRIP` 通知
- **When** 用户激活它
- **Then** 打开对应行程详情
- **And** 该条变为已读

#### Scenario: S30-22 申请类跳转
- **Given** 一条「申请到达」通知
- **When** 用户激活它
- **Then** 打开该行程的申请处理页
- **Given** 一条「申请已通过」通知
- **When** 用户激活它
- **Then** 打开对应行程详情

#### Scenario: S30-23 其它类型跳转
- **Given** 一条 `CHAT` / `CREDIT` / `REPORT` / `ACCOUNT` / `SERVICE` / `SYSTEM` 通知
- **When** 用户激活它
- **Then** 分别打开该会话、信用记录页、该举报详情、本人账号状态页、客服入口、身份资料页
- **And** 安全提醒类的 `SYSTEM` 通知打开对应行程详情

#### Scenario: S30-24 目标不可用
- **Given** 一条通知的关联对象已不可访问
- **When** 用户激活它
- **Then** 正文仍完整展示
- **And** 条目标记「相关内容当前不可查看」
- **And** 不发生页面跳转，也不出现错误提示
- **And** 该条仍变为已读

### Requirement: 未读计数与标读规则

系统 MUST 提供按用户读取的未读计数，包含总数与八类分项，且八类键 MUST 全部出现、零值 MUST NOT 省略。未读 MUST 由未读通知记录（已读时间为空）派生，MUST 在页面刷新、重连或重新读取后与持久化状态一致。壳层 MUST 在通知入口以数字显示未读总数，MUST NOT 仅以颜色表达；聊天入口与会话列表 MUST 显示 `CHAT` 未读数；数量为 0 时 MUST NOT 显示徽标。用户打开一条通知时，系统 MUST 只把该条标为已读；用户选择「全部已读」时，系统 MUST 把该用户的全部未读通知标为已读；用户打开某个会话时，系统 MUST 只把该会话（行程与对方用户共同限定）的 `CHAT` 通知标为已读。标读 MUST 幂等，且 MUST 只影响发起标读的用户自己的通知；对他人通知标读 MUST 返回未找到。

#### Scenario: S30-25 八类计数
- **Given** 用户有若干未读通知
- **When** 读取未读计数
- **Then** 总数等于八类分项之和
- **And** 八类键全部出现，未使用的类型为 0

#### Scenario: S30-26 徽标口径
- **Given** 用户存在未读通知
- **Then** 铃铛、侧栏通知中心入口与账号菜单入口显示未读总数
- **And** 侧栏与移动 tab 的聊天入口、以及会话列表显示 `CHAT` 未读数
- **When** 全部未读被清除
- **Then** 所有徽标消失，不保留仅有颜色的圆点

#### Scenario: S30-27 读一条
- **Given** 用户有若干未读通知
- **When** 该用户打开其中一条
- **Then** 该条变为已读
- **And** 未读总数与所属类型各恰好减 1

#### Scenario: S30-28 全部已读
- **Given** 用户有多条跨类型未读通知
- **When** 该用户选择「全部已读」
- **Then** 该用户所有未读通知变为已读
- **And** 总数与八类分项都为 0

#### Scenario: S30-29 幂等
- **Given** 一条通知已经是已读
- **When** 再次对它执行标读
- **Then** 未读总数与八类分项都不变

#### Scenario: S30-30 按用户隔离
- **Given** A 与 B 各有未读通知
- **When** A 把自己的通知标记为已读
- **Then** B 的未读计数不变
- **And** A 尝试标读 B 的通知返回未找到

#### Scenario: S30-31 会话范围
- **Given** 用户有两个会话各有未读聊天消息，且有其它类型的未读通知
- **When** 该用户打开其中一个会话
- **Then** 只有该会话的 `CHAT` 通知变为已读
- **And** 另一会话的 `CHAT` 与其它类型仍未读

#### Scenario: S30-32 计数不回弹
- **Given** 一条通知的已读时间已经落库
- **When** 页面刷新或在途快照落地
- **Then** 该条不再计入未读
- **And** 总数与所属类型保持已减后的值

### Requirement: 实时投递与失败隔离

系统 MUST 通过按用户的服务器推送通道，在通知创建后 3 秒内把该通知推送给收件人已打开的会话，且 MUST NOT 推送给其他用户。连接 MUST 由周期心跳保持，并 MUST 在客户端断开后释放。每次连接建立后，客户端 MUST 重新读取通知列表与未读计数，使漏推与重连收敛到持久化状态且不产生重复条目。推送通道不可用时 MUST NOT 影响应用其它功能，最后一次已知计数 MUST 保持可见，MUST NOT 出现阻塞式错误弹窗。任一业务动作触发的通知写入或推送失败时，系统 MUST 记录失败并仍向调用方返回该动作既有的成功结果。

#### Scenario: S30-33 三秒内只推收件人
- **Given** 收件人的推送通道已连接
- **When** 一条通知被创建
- **Then** 客户端在 3 秒内反映该通知，无需刷新页面
- **And** 其他用户的通道不收到该通知

#### Scenario: S30-34 重连对账
- **Given** 推送通道断开期间发生过通知
- **When** 客户端重连
- **Then** 它重新读取列表与计数
- **And** 计数与持久化状态一致且没有重复条目

#### Scenario: S30-35 通道失败可控
- **Given** 推送通道无法建立或中途失败
- **When** 用户继续使用应用
- **Then** 其它功能照常可用
- **And** 最后一次已知的未读计数仍显示
- **And** 不出现阻塞式错误弹窗

#### Scenario: S30-36 失败隔离
- **Given** 通知写入或推送发生失败
- **When** 用户提交申请、发布者裁决、用户发消息、信用变动、举报处理、账号状态变更或客服动作
- **Then** 对应业务动作仍然成功
- **And** 调用方仍收到既有的成功结果
- **And** 失败被记录，供排障使用
