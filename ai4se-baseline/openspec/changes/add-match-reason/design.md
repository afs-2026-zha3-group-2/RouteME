# 设计：add-match-reason

## 结论

匹配能力已在 `add-trip-companions` 落地，本次不改表结构、不改端点形状。工作是把打分口径与降级文案写成可判定场景，并按场景补断言；只有断言暴露出缺口时才改 `TripMatch` / `MatchServiceImpl`。

## 关键取舍

### D1 打分口径放在哪一层

| 方案 | 行为 | 结论 |
|---|---|---|
| 前端算分 | 列表与详情各自实现权重，容易漂移 | 否决 |
| 后端纯计算服务 `TripMatch` | 单点定义权重，列表、详情、排序共用 | 采用 |

理由：排序（`sort=match`）、列表徽标、详情面板三处消费同一分值，必须只有一个权威实现。`TripMatch` 是无状态纯计算，不持有数据表，符合 `package-structure` 对计算服务的定位。

### D2 百分比与分值的关系

`score` 已是 0–100 分制，`percentage` 直接等于 `score`，不再做二次归一。若未来放开权重总和，需要重新定义归一公式；当前保持同值最省歧义。

### D3 降级文案的边界

| 场景 | 参照物 | 文案 |
|---|---|---|
| 用户已发布过行程 | 最近一条未结束的已发布行程 | 「对照你发布的《标题》」+ 命中维度 |
| 用户尚未发布行程 | 当前筛选条件与用户兴趣 | 「对照你的旅行兴趣」+ 命中维度 |
| 无任何重合 | 同上 | 「暂无重合，可作为新方向的灵感」 |

三种文案都必须非空，`reasons` 至少一条。百分比在降级文案下仍展示，但原因文本必须独立可读（去掉百分比后语义完整）。

### D4 展示位置

列表卡片显示「匹配度 N%」与「匹配理由 …」，环形图只作装饰；详情页显示原因列表 + 「匹配度 · 参照物」。两处共用 `Match` 对象，避免二次请求；详情页通过 `GET /api/matches/{tripId}` 单独取，保证直接打开详情也有原因。

## 风险与例外

- **风险：** 原因文本会随标签数量增长，卡片高度不稳定。当前限制共同兴趣最多列出命中的全部兴趣，标签上限 5，可接受。
- **例外：** 按匹配度排序已在 `add-paged-lists-mybatis-plus` 实现，本 change 只登记场景，不重复改排序代码。
- **遗留：** 匹配不考虑预算、集合区域与性别偏好，属产品后续范围。

## D11 R2 匹配只认个人参照（2026-11-16）

| 方案 | 行为 | 结论 |
|---|---|---|
| 保留筛选作为参照（现状） | 同一行程在筛选列表得 50、详情得 0；与 REQ-007「匹配规则不变」冲突 | 否决 |
| 让详情也接收筛选参数 | 需要把首页筛选状态带进详情 URL，跨页状态扩散，且详情本身没有筛选语义 | 否决 |
| 匹配只由「最近一条未结束的已发布行程 / 我的兴趣」决定，筛选只筛选与排序 | 列表与详情天然一致；`basis` 与理由自洽 | 采用 |

实现约束：

- `TripMatch.of(candidate, reference, interests)`：删除 `filterDestinationCode` / `filterDate` 参数与「筛选覆盖参照物」分支。
- `MatchServiceImpl` 的 `search` 与 `matchFor` 共用同一计算入口，不再分别传筛选。
- 契约 `Match.basis` 描述改为「最近一条未结束的已发布行程，或你的旅行兴趣；筛选与排序不影响匹配分」，版本 0.8.0 → 0.8.1。
- 单元测试：删除 `in_filterDestination_out_overridesReference`，改为「参照目的地不同则不计目的地分」；接口测试新增「筛选前后同一行程分值不变、列表与详情一致」。
