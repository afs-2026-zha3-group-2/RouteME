# 变更提案：add-credit-account

- **需求来源：** 用户故事「作为平台用户，我希望查看自己的信用分和信用等级，以便了解自己当前在 RouteMe 平台的信用状态」（P0 / 信用系统迭代 1 / 2 点 / 落点 用户个人主页 + 管理后台用户详情页）｜ **需求条目：** `requirement-workspace/requirements/REQ-019-credit-account.md`
- **能力：** `user-credit`（ADDED）；只读依赖 `user-profile` / `user-profiles`（均未归档）；`user-auth` 仅作注册集成点（D9：不改其 Requirement）
- **规模：** S–M（新增 2 张表 + 1 次回填迁移 + 1 个记账服务 + 1 处响应字段扩展 + 1 处页面展示；无新页面、无新路由、无新端点）
- **规则：** `@rule:api-contract`、`@rule:java-patterns`、`@rule:web-coding-style`、`@rule:security-baseline`、`@rule:tdd-cycle`、`@rule:prototype-ui-alignment`、`@rule:sdd-artifacts`

## 问题

RouteME 现在有账号、资料、行程、同行申请、聊天与体验，但没有任何「信用」概念：`app_users` 只有身份与资料列（`V3` / `V10`），注册链路只建账号与会话，个人主页（`#/users/{id}`）只展示身份与资料。平台下一步要用「信用分」承载同行信任——先解释「这个人靠不靠谱」，再承接后续的加分（体验获赞）与扣分（退出、举报核实）——但当前连一个可展示的分数都不存在：

- 新账号没有初始分，老账号（4 个演示用户 + 已注册账号）没有回填口径；
- 没有等级定义，也没有「必须同时显示分数与文字」的约束；
- 没有账本，任何未来的分变都无处留痕，「变更前 + 变更值 = 变更后」无法校验；
- 没有结构性只读保障，分数字段一旦散落在资料写接口里，就会被用户自己改掉。

本变更只做这条链的**第一段垂直切片**：用户创建 → 初始化信用账户 → 展示信用状态。计分事件与管理后台**不在本变更**。

## 范围

**In scope**

- `user-credit`（ADDED）：信用账户（每用户一条、区间 0–100）、初始值 80、历史账号回填、五档等级派生、个人主页展示口径、只读约束、信用记录与记账服务、越界裁断、幂等键预留。
- 数据：新增 `user_credit_account` 与 `credit_ledger`；新增一次迁移（建表 + 回填全部既有账号 80）；**不改** `app_users`。
- 注册集成：`AuthServiceImpl.register` 在同一事务内初始化信用账户（80）；失败分支不落账户。
- 个人主页：`GET /api/users/{userId}/profile` 响应追加只读信用字段（分数 + 等级），本人与他人同口径；`ProfilePage` 新增信用状态展示（分数 + `/ 100` + 等级文字）。
- 记账服务：内部能力，完成 0–100 裁断、实际生效量、前 / 后快照、账本与账户同事务写入、幂等键唯一约束，并配单元测试；**本变更无业务事件调用方**。
- 契约：`openapi.yaml` 升次版本 + `UserProfile` 追加只读字段；同步后端契约测试与前端类型。
- 故事与登记：`stories.md` / `registry.md` / `handoff.md` 登记 REQ-019 → `add-credit-account`。

**Out of scope**

- **管理后台全部内容（用户裁决 D2 推迟）：** 用户列表、用户详情、按信用分排序、按信用等级筛选、管理员身份与权限模型；对应故事 AC3 / AC4，以及 AC6「管理端一致」的后半句。归档时在 Delta 中保留「本迭代不提供管理后台展示」的显式约束。
- 任何产生分变的业务事件：体验获赞阶梯加分与月度上限、出发前退出扣分阶梯与月度累进、旅行中退出扣分、举报核实扣分、自动封禁（< 60）、安全学习恢复。
- 分数调整 / 回滚 / 后台手工改分 / 申诉通道。
- 规则说明页、分数变化历史页、明细对用户可见的任何形态。
- 他人主页之外的展示触点：行程卡、`ProfileModal`、申请列表、我的旅行资料卡、顶栏。
- 通知 / 推送 / 邮件；等级色板与徽章视觉重做。
- 引入第二套 UI 组件库或独立「信用中心」页面。

## 决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 分数口径 | 0–100；90 / 80 / 60 / 30 四道阈值（用户裁决 D1） | 历史会话中的「信誉分 0–120、六档、低于 60 自动封禁」方案与本次故事冲突，按「以本次故事为准」作废；本变更不引入封禁 |
| 管理端 | 本轮只做用户端（用户裁决 D2） | 仓库里没有角色列、后台端点或后台页面，从零建后台会把 2 点故事扩成两个功能；推迟到独立故事更可验收 |
| 数据模型 | 账户表 + 账本表（用户裁决 D3） | 分数唯一真相单点存放；账本可回算、可审计；避免 `app_users` 出现「一份分数两处写」 |
| 可见性 | 本人与他人同口径，明细不展示（用户裁决 D4） | 信用分的价值在于同行判断，只给自己看没有意义；但加扣分原因是敏感信息，不对外 |
| 历史回填 | 统一 80（用户裁决 D5） | 与初始值一致，等级一律「信用良好」；避免为演示用户编造差异化分数 |
| 记账能力 | 本变更落地记账服务（用户裁决 D6） | 「不可越界 / 不可自改 / 每次变化留痕」是结构性保证，越晚补越容易在业务事件里散落；本变更用单测锁定不变量 |
| 接口归属 | 扩展个人主页响应（用户裁决 D7） | 页面零额外往返、只有一个加载态；与 `add-user-profile` / `add-user-profiles` 的既有响应演进方式一致 |
| 命名 | `add-credit-account` / `user-credit`（用户裁决 D8） | 与「账户 + 等级展示」的切片范围一致 |
| 能力归属 | 信用字段写在 `user-credit`（ADDED），**不** MODIFY `user-profile` | `user-profile` 的 Delta 仍未归档，改它会在归档时与本变更抢同一 Requirement 块；由 `user-credit` 拥有信用字段的语义，`user-profile` 保持原语义 |
| `user-auth` 归属（D9） | 不改 `user-auth`「注册账号」 | 保持单 capability；「注册后建账户」由 `user-credit` 的场景覆盖，归档无需双 capability 例外追认 |
| 等级契约取值（D10） | 接口返回英文码 `excellent` / `good` / `fair` / `low` / `risk`，展示文案由前端 i18n 映射 | 契约稳定、文案可改；五档阈值只在服务端一处实现，避免前后端各存一套 |
| 等级存储 | 读取时派生，不落库 | 避免「分数改了等级没改」的漂移；五档阈值只存在一处 |
| 序列化 | 信用字段必须为非空值 | `UserProfileResponse` 使用 `@JsonInclude(NON_NULL)`，可空字段会被整键省略，会破坏「任意用户不出现缺失值」 |
| 缺失账户 | 读取路径必须有确定性兜底（懒建或回填保证） | 不允许出现「有用户无信用分」的半状态；具体机制由 P3 定 |
| 全裁断留痕（D11） | 实际生效量为 0 时**仍写一条 `applied_delta = 0` 的记录**（分数不变） | 与故事「每次变化必生成记录」一致，保留事件痕迹与幂等键；本变更用单测锁定该分支 |

## 验收信号

1. 新用户注册成功后打开个人主页，看到「信用分：80 / 100 · 信用良好」。
2. 4 个演示用户与变更前已注册的账号打开个人主页，同样显示 80 分与「信用良好」，不出现空值、0 分或错误页。
3. 同一用户重复登录、刷新主页，分数不变，账户仍只有一条。
4. 分数取 100 / 90 / 89 / 80 / 79 / 60 / 59 / 30 / 29 / 0 时，等级依次为优秀 / 优秀 / 良好 / 良好 / 一般 / 一般 / 较低 / 较低 / 风险 / 风险，无空档。
5. 页面同时输出具体分数与等级文字，不存在「只有颜色或只有数字」的展示。
6. 他人打开同一主页看到同一分数与等级；页面没有加扣分明细、原因、时间或历史入口。
7. 用户在保存资料时附带信用分字段，分数保持不变；仓库中不存在任何客户端可调用的写分端点。
8. 一次 +5 变化作用在 98 分上，分数停在 100，记录为「变更前 98 / 实际 +2 / 变更后 100」；3 分遇 -10 停在 0 并记录 -3。
9. 89 分经 +1 变化后立即展示 90 分与「信用优秀」，无需额外刷新。
10. `openspec validate add-credit-account --strict` 通过；既有注册 / 登录 / 会话 / 资料 / 行程 / 申请 / 聊天 / 体验 / 举报不回归。

## 残余风险

| 风险 | 处理 |
|---|---|
| 契约版本号与在途 change 撞号（REQ-017 已声明 0.12.0） | P3 按合并顺序排他确认后只升一次次版本；不预设具体号 |
| 迁移号与 REQ-016（V17）/ REQ-017（V18）冲突 | 迁移号在 P3 确认；建表 + 回填写在同一个迁移内，避免半成品库 |
| `NON_NULL` 序列化静默省略信用字段 | 后端字段必须非空；契约测试与 E2E 都断言「他人视角也含该键」 |
| 回填只覆盖有登录凭据的账号 | 回填按 `app_users` 全表；E2E 覆盖 id 4 周野等无凭据账号 |
| 与未归档 change（`add-user-profile` / `add-user-profiles`）交叉 | 本变更只追加只读字段、不改其 Requirement 语义；归档顺序不构成阻塞 |
| 管理端三条 AC 被误读为「未完成」 | 需求 / 提案 / Delta / registry 四处均写明 D2 推迟范围；Delta 另有「管理后台信用分视图与计分明细的边界」的显式约束 |
| 原型无信用分骨架 | `@rule:prototype-ui-alignment`；P3 先补原型截点再实现 |
| 等级英文码与前端文案不一致 | 契约固定五个码值（`excellent` / `good` / `fair` / `low` / `risk`），前端映射集中在 i18n；契约测试断言码值集合，E2E 断言展示文字 |
