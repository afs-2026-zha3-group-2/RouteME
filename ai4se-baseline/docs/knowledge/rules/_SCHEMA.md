# 规则文件格式（本项目约定）

本文件取代 rulepack 的默认 schema。默认 schema 是「一条规则一个文件、文件名等于 ID」，本项目改为**每个分类一个文件**，原因见 [为什么这样定](#为什么这样定)。

## 目录约定

```text
docs/knowledge/rules/
├── _SCHEMA.md        本文件：格式约定
├── _INDEX.md         索引（规则 ID → 锚点）
├── _LOG.md           变更日志（只追加）
├── README.md         分类总览、团队原则与来源裁决
├── process/rules.md
├── architecture/rules.md
├── quality/rules.md
├── testing/rules.md
├── security/rules.md
├── documentation/rules.md
└── modules/<id>/rules.md    单模块覆盖（仅在确有需要时创建）
```

**一个分类目录下只有 `rules.md` 一个文件。** 不新增 `__*.md`、`README.md` 或按规则拆分的文件；分类内的增删改直接改 `rules.md`。

## 规则 ID 即锚点

- 规则 ID 写成二级标题：`## <id>`，例如 `## git-commit-conventions`。
- 中文规则名写在紧跟标题的一行加粗文本里，**不写进标题**，否则 GitHub 会把中文标题转成变形锚点，`#<id>` 就失效。
- 外部引用统一用 `@rule:<id>` 或 `rules/<category>/rules.md#<id>`，两种写法都解析到同一个二级标题。
- ID 一旦发布就不改名、不复用。规则被合并时保留承接规则的 ID，并在 `_LOG.md` 记录「哪个 ID 并入哪里」；规则被删除时同样记录。

## 单一事实源（本项目的核心约束）

每条规范只在一个规则里写正文，其它位置只写 `@rule:<id>` 指针，不复制条款、例子或表格。权威分配如下：

| 主题 | 权威规则 |
|---|---|
| 金额字段语义、术语、跨端命名 | `naming-conventions` |
| 分层、包/目录分类、依赖方向、类名后缀 | `package-structure` |
| 契约字段、路径、状态码、版本兼容 | `api-contract` |
| 持久化（迁移、UTC 时钟、行对象、仓储/端口位置） | `java-patterns` |
| Java 写法（金额、常量、异常、注释） | `java-coding-style` |
| 前端写法（组件、请求层、类型、样式、可访问性、i18n） | `web-coding-style` |
| 测试命名、结构与边界值 | `java-testing` / `web-testing` |
| 提交时机、message、提交前检查 | `git-commit-conventions` |
| 工件目录、命名与职责 | `sdd-artifacts` |

合并判断标准：两个规则描述同一决定且例外条件相同，就并成一条（如「分层」与「依赖方向」）；只是引用同一事实的两条规则，保留各自 ID，把重复正文改成指针。

## 文件结构

每个 `rules.md` 按下列顺序组织，缺段要说明原因：

| 顺序 | 节 | 内容 |
|---|---|---|
| 1 | `# <中文名>规则（<category>）` | 一级标题，括号内是英文分类名 |
| 2 | 首段说明 | 一句话说明本文件是该分类的权威正文、ID 即锚点 |
| 3 | `## 适用范围` | 本分类管什么、不管什么、跨分类边界指向哪里 |
| 4 | `## 规则总表` | 全分类一张表：ID / 规则 / 优先级 / 触发 / 适用栈 |
| 5 | `## <id>` × N | 每条规则一节，见下 |
| 6 | `## 为什么这样定` | 全分类共用的立规理由（一段，不逐条复述） |

分类末尾**不再**设「全分类检查清单」：检查项在各规则的「检查项」表里已经可判定，重复汇总只会出现两份措辞不同的判据。

## 单条规则的小节

`## <id>` 之下按需包含，不适用的省略：

1. **规则正文** — 紧跟标题的加粗一句话，再用列表写规范条款（陈述句，可判定）。
2. **补充说明** — 分主题的小节（如 `### 命名`、`### 金额`），只写本规则独有的内容。
3. **检查项** — 表格：检查 / 阻断点；每个检查项能在代码或工件上判定。
4. **示例** — 按需。条款已自明时不写；写则用 `推荐 / 不推荐` 或 `// 推荐 / // 不推荐`，例子必须来自本仓库真实代码。
5. **例外** — 没有就写「例外：无。」。

## 规则总表字段

| 字段 | 取值 |
|---|---|
| ID | 稳定 id，kebab-case，例如 `spec-first` |
| 规则 | 一句话中文说明 |
| 优先级 | Critical \| High \| Medium \| Low |
| 触发 | always \| auto \| manual |
| 适用栈 | `—`（不限）或 `java`、`react`、`typescript` 等，逗号分隔 |

## 语言

正文中文；代码、标识符、命令、字段名、文件路径、commit message 保留英文。`SHALL` / `MUST` 等结构关键词保留英文。术语以 [quality/rules.md](quality/rules.md#naming-conventions) 的术语表为准，不用同义词轮换。

## 为什么这样定

一条规则一个文件时，规则总数就是文件数，按分类浏览要逐个点开，跨规则的一致性（同一套金额字段、同一套检查阻断点）无从校验。合并成每分类一个文件后，入口从几十个降到 6 个，分类内可以直接比对、去重、统一术语；代价是单文件变长，靠二级标题与「规则总表」保持可跳转。

ID 仍做二级标题，是为了让 `@rule:<id>` 与索引里的 `#<id>` 在合并后继续有效。真正需要控制的是**重复**而不是行数：同一决定写两遍，改一处就会留下两个互相矛盾的版本，评审时无法判断哪条有效。
