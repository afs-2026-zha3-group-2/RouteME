## 1. Intent

一句话：让**刚注册的新用户**在一个完善页上补齐**头像、昵称、生日、性别、所在城市、学校、专业、职业、MBTI、旅行兴趣、旅行方式和个人简介**并保存；系统根据生日**自动生成年龄与星座**，保存成功后进入**个人主页**，其他人在查看该用户发布的行程时能从发布者入口看到同一份资料。因为当前资料只够「认出这个人」，不够「判断要不要一起走」，而注册表单又不该承担资料收集的职责，所以需要一次从「账号」到「可展示的人」的补齐动作。

## 2. Actors

| 角色 | 权限边界 |
|---|---|
| 新注册用户 | 注册成功即进入资料完善页；可跳过，稍后从「我的」补全；可编辑并保存自己的资料。 |
| 已注册用户 | 可随时编辑自己的资料并重新保存；资料变更对其他查看者立即生效。 |
| 浏览者（其他已进入用户） | 可从行程卡 / 行程详情的发布者入口查看对方个人主页；不能编辑。 |
| 演示身份 | 资料只读；可被浏览者查看；没有「完善资料」入口，也不能调用保存接口。 |
| 访客（未进入） | 不展示个人主页入口；直接访问时回到身份门，不泄露资料。 |

不新增角色；个人资料只能由本人修改，其他人只读。

## 3. In / Out scope

**In scope**

- 注册表单瘦身为用户名 / 密码 / 昵称；注册成功后进入个人资料完善页（用户裁决 D3）。
- 新增个人资料完善页：头像（选填、真实上传）、昵称、生日、性别、所在城市、学校（选填）、专业（选填）、职业（选填）、MBTI（选填）、旅行兴趣（3–5 个）、旅行方式（单选）、个人简介（选填）。
- 生日派生年龄与星座：服务端按当前日期计算，资料响应只返回年龄与星座，不返回完整生日。
- 必填校验：昵称、生日、性别、所在城市、旅行兴趣（≥3）、旅行方式；缺失时阻止提交，并逐项标出未完成字段与汇总提示。学校、专业与职业均不参与必填校验。
- 保存资料并进入本人个人主页；个人主页支持本人再次编辑。
- 其他用户从行程卡 / 行程详情的发布者入口进入个人主页；未完善资料时展示已有字段与「资料尚未完善」提示。
- 资料完善状态由必填字段派生；允许跳过并在「我的」中补全（用户裁决 D4）。
- 头像缺省回退昵称首字，保证任何展示位不出现空头像。

**Out of scope**

- 手机号 / 邮箱验证、实名认证、第三方登录、改密码 / 找回密码、账号注销。
- 头像裁剪编辑器、相册、背景图、动态、关注、私信。
- 资料可见性与按字段屏蔽、访客可见性差异、隐私开关。
- 旅行兴趣词表与行程标签的匹配算法统一（P3 设计项，本需求只要求 3–5 个可保存）。
- 演示身份的资料编辑、演示账号数量与进入 / 切换行为。
- 行程、申请、聊天、体验的业务规则变更。

## 4. Scenarios + AC hints（SHALL 式，可观察）

1. **注册后进入资料完善页** — Given 访客用合法用户名、密码与昵称完成注册，When 注册成功，Then 系统 SHALL 建立会话并把该账号标记为「资料未完善」，前端 SHALL 进入个人资料完善页；页面 MUST NOT 要求再次输入用户名或密码。
2. **提交完整资料并生成个人主页** — Given 资料未完善的注册用户填写了全部必填项，When 用户提交，Then 系统 SHALL 保存资料、把状态变为「资料已完善」，并进入该用户的个人主页；主页 SHALL 展示刚保存的字段与派生的年龄、星座。
3. **生日派生年龄与星座** — Given 用户填写生日 `2003-05-18`，When 保存或查看资料，Then 系统 SHALL 按当前日期计算并展示周岁年龄与星座；生日本身 MUST NOT 对其他人展示。
4. **必填缺失阻止提交** — Given 用户只填了昵称与生日，When 用户尝试提交，Then 前端 MUST NOT 发出保存请求，并 SHALL 在对应字段标错、同时给出「还有 N 项未完成」类汇总提示，明确指出缺失的字段名称（性别、所在城市、旅行兴趣、旅行方式）。
5. **上传头像（选填）** — Given 用户在完善页选择一张合法图片，When 上传成功，Then 系统 SHALL 保存该头像并在预览、个人主页与发布者入口展示；不上传头像 MUST NOT 阻止提交。
6. **无头像时回退** — Given 用户没有上传头像，When 资料展示在个人主页或行程卡，Then 系统 SHALL 用昵称首字作为头像占位，MUST NOT 出现空白头像框。
7. **学校、专业与职业分开录入** — Given 用户填写学校「中山大学」、专业「地理科学」并选择职业「学生」，When 查看资料，Then 展示为「中山大学 · 地理科学」与职业「学生」；三字段 MUST 分别录入，用户不需要输入间隔号 `·`；只填职业或只填学校时 SHALL 只展示已填内容，MUST NOT 用占位符伪造缺失字段。
8. **兴趣至少 3 个、最多 5 个** — Given 用户尚未选够 3 个旅行兴趣，When 用户尝试提交，Then 系统 MUST 阻止提交并提示「至少选择 3 个兴趣标签」；选满 5 个后 MUST 阻止继续添加，自定义标签取消后仍保留可复选。
9. **旅行方式单选** — Given 用户选择「深度游」，When 用户改选「随性游」，Then 系统 SHALL 只保留最后一项；旅行方式 MUST NOT 多选。
10. **选填项留空** — Given 用户只填写了全部必填项，When 用户提交，Then 系统 SHALL 接受并保存，头像、学校、专业、职业、MBTI 与个人简介可以为空。
11. **跳过并稍后补全** — Given 新注册用户选择跳过完善页，When 用户进入首页或「我的」，Then 系统 SHALL 允许继续浏览与使用既有功能，并在「我的」保留「完善资料」入口；补全并保存后状态变为已完善。
12. **他人从发布者入口查看** — Given 浏览者在行程卡或行程详情看到发布者，When 点击发布者，Then 系统 SHALL 打开该用户的个人主页，展示允许公开的资料字段；MUST NOT 进入编辑态。
13. **查看未完善资料** — Given 发布者尚未完善资料，When 其他用户打开其个人主页，Then 系统 SHALL 展示已有字段（昵称、头像 / 首字，以及已填的学校或职业），并提示「该用户尚未完善资料」；MUST NOT 报错、展示空白页或伪造未填字段。
14. **再次编辑已保存资料** — Given 用户资料已完善，When 用户从个人主页点击编辑并修改旅行方式后保存，Then 系统 SHALL 覆盖原资料并立即在其他展示位生效，MUST NOT 创建第二份资料。
15. **生日非法** — *（异常）* Given 用户填写未来日期、无法解析的日期或早于 1900-01-01 的日期，When 用户提交，Then 系统 MUST 拒绝保存并提示生日不合法；其他字段 MUST NOT 被部分写入。
16. **未登录或演示身份保存被拒绝** — *（边界）* Given 请求没有有效会话，或当前身份是演示账户，When 调用保存资料 / 上传头像接口，Then 系统 MUST 返回 401 / 403；演示身份界面 MUST NOT 展示「完善资料」或「编辑资料」入口。
17. **头像文件不合法** — *（边界）* Given 用户选择的文件超过大小上限或不是允许的图片类型，When 上传，Then 系统 MUST 拒绝并提示可读原因；已填写的其他字段 MUST NOT 丢失。

## 5. Constraints（仅事实，不含技术方案）

- 字段长度沿用既有账号口径：昵称 ≤20、学校 ≤80、简介 ≤500；新增专业 ≤80、职业 ≤20、城市 ≤40，兴趣每个 ≤12。
- 生日格式为 `YYYY-MM-DD`，不得晚于当天、不得早于 1900-01-01；年龄按周岁计算。
- 必填项固定为：昵称、生日、性别、所在城市、旅行兴趣（≥3）、旅行方式；头像、学校、专业、职业、MBTI、个人简介为选填。**原始 AC 的「头像必填」已被裁决 D1 覆盖，「学校必填」已被裁决 D2 追加覆盖。**
- 性别为单选，取值为「男 / 女 / 其他」；职业为单选，取值为「学生 / 上班族 / 自由职业 / 其他」；旅行方式为单选，取值为「特种兵 / 休闲游 / 深度游 / 随性游」；MBTI 为 16 型单选。
- 学校、专业与职业可同时为空；职业与学校互不排斥，可同时填写。展示时学校与专业拼为「学校 · 专业」，职业单独展示；缺失字段直接省略，不显示空占位。
- 旅行兴趣为 3–5 个，预设标签 MUST 至少覆盖 AC 列出的 10 个（美食、摄影、徒步、Citywalk、自然风景、文化历史、看展、音乐、户外、探店），允许自定义标签；取消后的自定义标签仍保留为未选卡片。
- 头像必须是真实上传的图片文件（用户裁决 D1），限制类型为 JPEG / PNG / WebP，单文件 ≤2 MB；未上传时回退昵称首字。
- 完整生日、密码、用户名不得出现在他人可见的资料响应中。
- 资料保存接口只能作用于当前会话用户；演示账户只读。
- 个人主页与完善页需键盘可达，字段错误与汇总提示需可被读屏软件读出。
- 不新增依赖、不改设计系统；沿用现有页面外壳与组件。
- 既有注册、登录、会话恢复、退出、行程、申请、聊天与体验行为不得回归。

## 6. Context

`add-user-auth` 已归档并进入 Living Spec：注册时一起收集昵称、学校、简介与兴趣，注册成功直接进入首页；`GET /api/users/{id}` 等既有接口只返回昵称、首字、学校、简介与兴趣（`DemoUser`）。`trip-plans` / `trip-experiences` 的发布者展示复用这套字段。用户现在要求把「注册」与「资料」分开：注册只负责创建账号，资料在一个独立页面上补齐，保存后生成可被他人查看的个人主页，并补上生日、性别、城市、专业、职业、MBTI、旅行方式与头像。由于这既改注册流程（`user-auth`），又新增资料与主页能力（`user-profile`），本需求是一次**双 capability 的页面级垂直切片**，归档前需 SA 追认该例外（与 REQ-005 同口径）。
