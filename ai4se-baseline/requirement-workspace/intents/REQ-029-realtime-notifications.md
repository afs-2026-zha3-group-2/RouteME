# REQ-029 — 实时通知中心与未读计数（意图捕获）

- **捕获日期：** 2026-11-17（初次）｜ **扩围日期：** 2026-11-18
- **捕获人：** Karena（本次 change 的当前开发者）
- **来源：** 发起人在 `http://localhost:5173/#/chat` 的观察——「申请到达 / 我的申请被接受 / 收到新消息都没有实时通知，也没有像圆点那样显示收到几条通知的指示」；2026-11-18 进一步要求把通知扩展为覆盖八类业务事件的完整**通知中心**
- **Change：** `add-realtime-notifications`
- **能力：** `notifications`（ADDED）

## 原始意图

在使用聊天页与其它页面时，发起人发现没有任何东西会宣布三类事件：

1. 有人申请了自己发布的行程；
2. 自己提交的申请被接受；
3. 收到一条聊天消息。

唯一发现它们的办法是进到对应页面并刷新。发起人要求两件事：

- 这些事件发生时给出实时提示；
- 一个可见的指示（圆点 / 带数字的圆圈）显示还有多少通知未处理。

## 扩围后的意图（2026-11-18）

发起人确认：不只做「申请 + 消息」的提示条，而是把**所有需要用户知道或行动的业务事件**收进同一个通知中心，避免用户为了不同事件记住不同的入口。扩围后的八类事件：

| 类型 | 业务事件 |
|---|---|
| `TRIP` | 行程满员、进入旅行中、被取消、已结束 |
| `APPLICATION` | 收到申请、申请通过、申请被拒、申请因行程取消而关闭 |
| `CHAT` | 收到同行者消息 |
| `CREDIT` | 信用分变动（含扣分、加分、低分限制、完成安全学习后的恢复） |
| `REPORT` | 举报提交成功、进入处理中、处理完成 |
| `ACCOUNT` | 账号被暂停、被封禁、限制解除 |
| `SERVICE` | 人工客服接入、客服新回复、客服会话结束 |
| `SYSTEM` | 出行安全提醒、身份认证通过 |

每条通知都要能一键跳到仍然存在的目标对象；目标不可访问时保留原文并明确提示不可查看。

## 为什么重要

这些事件正是产品请用户行动或让用户安心的时刻：审阅申请、与同行者沟通、知道信用分为什么变化、知道举报有结果、知道账号受限与恢复时间。今天应用在页面加载之间是完全沉默的，用户可能整条错过一次申请、一次裁决或一次处罚说明。

## 发起人给出的约束

- 指示必须在聊天页之外也可见，不能只在 `#/chat` 里。
- 计数必须显示为数字，不能只有颜色。
- 未读徽标出现在通知中心入口（侧栏与账号菜单），不只出现在铃铛上。
- 通知不能因为关联业务状态变化而被删除；已读操作也不能改动业务状态。
- 通知中心要有按类型筛选与「全部已读」。
- 既有壳层布局必须继续正常工作（主题切换已由 `main` 移除，本 change 只保留浅色走查）。

## 明确排除

- 邮件、短信、OS 级推送、浏览器关闭时的通知。
- 通知偏好设置、保留策略、搜索。
- 申请、聊天、信用、举报、账号、客服、行程状态规则的改动。
- 推送通道的真实鉴权；沿用既有 demo 身份模型。
- 移除既有 3 秒聊天轮询（保留为兜底）。
