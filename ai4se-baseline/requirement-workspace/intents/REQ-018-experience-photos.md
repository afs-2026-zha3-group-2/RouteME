## 原始意图（一句话）

作为已经结束旅行、正在发布或修改游后体验的用户，我希望给体验补上最多 6 张真实行程照片，让后来者看到文字之外的现场；作为浏览者，我希望在原行程详情页看到这些照片，而首页体验卡继续用内置封面保持列表轻量。

## 为什么（价值假设）

文字体验已经能承接「强度 + 一条建议」，但真实照片能显著提升可信度与灵感转化，也让「参考此行程发布」更有依据。S16 在原型里把图片上传明确列为**增强项**，工期紧张时第一条削减的就是它；现在主线已交付，补齐这条增强比新开一条故事更贴合产品闭环。价值假设是：**照片只增加体验的可信度，不改变发布资格、文字口径与首页信息密度**。

## 用户裁决（2026-11-17）

| id | 议题 | 裁决 | 影响 |
|---|---|---|---|
| D1 | 存储与上传边界 | **两步上传 + 本地磁盘**：新增 multipart 上传端点，返回图片引用；体验提交只传有序图片引用数组；文件落 `SqlLite/uploads/experience-photos/`，复用头像的魔数校验与服务端文件名 | 新增端点与目录，不改部署形态 |
| D2 | 数据契约 | **≤6 张 / 单张 ≤5MB**；JPEG / PNG / WebP 按魔数判定；首图为主图；编辑时可增删与排序；替换或移除后旧文件由后端清理 | 契约入参与出参需带图片集合与顺序 |
| D3 | 展示位置 | **首页体验卡保持内置封面不变**；仅在原行程详情页与分享页展示图片 | `ExperienceCard` 不改视觉，不改首页 E2E 封面断言 |
| D4 | 范围与权限 | **仅游后体验（发布 / 修改）**；上传、删除、排序仅体验作者；浏览者只读；不含行程发布封面、聊天图片、头像、S17 | 单 capability `trip-experiences`，不扩 `trip-plans` |
| D5 | 缩略图 | **不生成服务端缩略图**；原图 + CSS 等比 + `loading="lazy"`，列表只加载首图 | 无图像处理依赖；性能不足时另开优化 |
| D6 | EXIF | **上传时全部剥离**（GPS、设备、拍摄时间） | 隐私优先；服务端保存的文件不含元数据 |
| D7 | 孤儿清理 | **懒清理**：每次上传时清理 >24 小时未绑定的图片 | 不引入定时任务；不影响已发布体验 |
| D8 | 内容审核 | **不做自动审核**，沿用举报入口与人工处理 | 不新增状态机；记为残余风险 |

## 意图边界（初判）

- **覆盖：**
  - 分享页的图片上传位（最多 6 张，预览、删除、排序、失败可重试）。
  - 图片格式 / 大小 / 数量校验，按魔数判定而不是扩展名。
  - 体验保存时携带有序图片引用；再次编辑时保留、增删与重排。
  - 原行程详情页的体验列表展示首图缩略图，并可查看全部图片。
  - 首页体验卡保持内置封面；无图体验与历史体验的行为不变。
  - 原作者可管理自己体验的图片；他人图片引用被拒绝。
- **不覆盖：**
  - 行程发布封面图、聊天图片、头像上传（归各自能力）。
  - 图片内容审核、AI 打标、外链图片、对象存储 / CDN。
  - 首页体验卡改图、图片轮播、瀑布流。
  - 「参考此行程发布」复制图片（S17 仍不带图）。
  - 删除体验端点（当前不存在）；图片生命周期只随体验编辑处理。

## 与现有 Living Spec / 能力的关系

- `trip-experiences` 的 Living Spec 规定「体验 MUST 以纯文字与项目内置封面展示」；本需求把图片变为**可选增强**，需要 MODIFIED 该 Requirement 的展示口径，但不改发布资格、字数与强度三档。
- `trip-plans` 只读消费：详情页新增体验图片展示位，不改行程模型与发布校验。
- `user-profile` 的头像上传是**实现先例**，不是能力依赖；不新增用户字段、不改头像端点。
- `openapi.yaml` 当前 0.11.0、迁移到 V17；本需求预期新增一个 multipart 端点与体验图片字段，版本与迁移号在 P3 与在途 `add-ai-itinerary`（计划 0.12.0 + V18）统一排号。
