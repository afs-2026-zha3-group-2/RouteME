## 原始意图（一句话）

作为行程发起人，我希望在旅行开始前取消自己发布的行程，并选择取消原因，以便在计划无法继续时及时终止招募，让已申请或已加入的用户看到「行程已取消」，同时保留历史数据。

## 为什么（价值假设）

现行系统只有「招募中 / 已满员 / 旅行中 / 已结束」四态，状态由完成时间、人数与日期推导（`TripPlan.java:59-70`），**没有取消态**。发布者一旦无法出行，只能把行程「标记为已结束」——这会把一条从未发生的行程伪装成已完成，并让已接受同行者进入「发表体验」环节；同时待处理申请、聊天与首页列表都没有「取消」语义。

`trip-plans` 的 Living Spec 已经写明「已结束与已取消行程 MUST NOT 出现在默认列表」，但代码里没有取消态，这条约束不可观测（历史评审 ASR-IH-02 已记录该漂移）。本需求把取消态补齐后，这条既有约束才真正可验证。

价值假设：**给发布者一个带原因、可确认、不可恢复的终止动作，并让所有相关角色在同一状态上收敛**——首页不再展示、申请关闭、聊天只读、我的旅行保留历史，从而避免「假结束」和悬空申请。

## 现状核对（2026-11-17，`origin/main@c1c238a`）

| 事实 | 证据 | 结论 |

## 意图边界

**覆盖：**

- 行程新增 `CANCELLED` 终态；仅发布者、仅在 `RECRUITING` 或 `FULL` 时可取消。
- 取消原因字典（8 项）：个人原因无法出行 / 行程时间发生变化 / 行程计划发生变化 / 同行人数不足 / 天气或不可抗力原因 / 突发疾病或受伤 / 安全原因 / 其他原因（说明必填 ≤100 字）。
- 二次确认：写明「取消后不可恢复」与影响（首页下架、待处理申请关闭、已匹配同行者可见）。
- 取消入口：行程详情页 + 我的旅行「我发布的」行内（用户裁决 D2）。
- 取消后联动：首页 / 匹配列表排除；申请入口关闭；PENDING 申请自动取消；ACCEPTED 同行者保留；聊天只读并提示「该行程已取消」；不能再结束、再次取消或编辑集合信息。
- 展示：详情与我的旅行显示「已取消」；原因与说明按 D3 裁剪可见；取消行程不出现「发表旅行体验」入口。
- 统计：发布者「发布行程」排除取消行程；「已完成」口径不变。
- 契约：`status` 增加 `cancelled`；新增取消端点与取消字段；迁移新增取消列。

**不覆盖：**

- 信用分、信用记录、扣分规则、免扣分申请、管理员审核（D1，属其他 story）。
- 删除行程、恢复 / 重新开启已取消行程、改期改线。
- 推送、短信、邮件等外部通知；只在站内页面展示取消结果。
- 取消原因的公开可见、评论或申诉流程。
- 已取消行程的体验发布、评价、退款或补偿。
- 修改 `trip-plans` / `trip-companions` 既有 Requirement 块中与取消无关的行为。

## 与现有 Living Spec / 能力的关系

- `trip-plans`：已拥有行程状态、列表与详情；Living Spec 已写明「已结束与已取消行程 MUST NOT 出现在默认列表」。本需求让「已取消」首次可观测，但不改写该 Requirement 块，取消的定义落在新能力 `trip-cancellation`。
- `trip-companions`：拥有申请与聊天。本需求只声明「取消后申请关闭、待处理自动取消、聊天只读」的取消侧约束；具体 Requirement 块由 `trip-cancellation` 承载，避免与未归档的 `add-trip-completion` / `refine-trip-application` / `refine-trip-chat` 三方同时改同一块。
- `trip-experiences`：只读消费「已结束」；取消行程天然不满足，故不改资格规则。
- `trip-plans` 的 `meeting` 维护：取消后不可编辑集合信息，由取消能力声明。

## Discovery Decision

`Go` — 候选能力可一句话说清（「发布者在招募中/已满员时取消自己的行程，进入终态并联动列表、申请、聊天、我的旅行与统计」）；与既有能力边界明确；用户已裁决入口、可见性、说明规则与归组；信用分明确排除；无阻塞项。日期：2026-11-17。
