## 原始意图（一句话）

我发布了一条行程，想知道「还有谁适合一起去」；系统应该按目的地、日期和共同兴趣帮我算清楚，并告诉我**为什么**推荐这个人。

## 为什么（价值假设）

现有 `trip-companions` 只回答「**这条行程**为什么匹配我」：

- `/matches` 的候选是行程，不是人；
- 理由是一句话，没有「目的地 +50 / 日期 +30 / 兴趣 +10」的分项；
- 同一个人有多条行程会重复出现；
- 详情页只有百分比，没有「可以找谁同行」的列表。

用户真正的决策是「找谁」，不是「看哪条行程的分高」。把推荐单元从「行程」换成「人（+其行程）」，并给出可解释分项，用户才能判断是否值得发出邀请。

价值假设：把「筛选 → 打分 → 去重 → 排序 → 解释」做成后端单一闭环，前端只负责展示，后续加预算、路线重合度、天气偏好时不需要改评分口径。

## 意图边界

**要覆盖：**

- 一条只读推荐接口：`GET /api/trips/{tripId}/recommendations`。
- 一套可解释评分：目的地相同 50、日期相同 30、相差一天 20、共同兴趣每项 10 且合计 ≤20。
- 候选筛选：开放行程、排除本人、排除参照行程自身、排除 0 分。
- 按用户去重、按总分倒序、同分按日期接近度。
- 响应包含用户、关联行程、总分、分项得分、共同兴趣。
- 详情页推荐区块：加载 / 成功 / 空状态 / 失败可重试。
- 用户切换行程、修改资料兴趣后重新请求。

**不覆盖：**

- 机器学习 / LLM 计算匹配分。
- 预算、路线重合度、天气偏好、信用分、旅行节奏等新特征（结构上留扩展点）。
- 邀请、申请、聊天流程改造。
- 地图探索页的 Mock 同行者面板（路线重合度展示线）。
- 数据库迁移。
