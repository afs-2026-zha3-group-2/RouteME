# RouteMe 路觅：8 天 MVP 完整设计方案

## 1. 产品定位

RouteMe 路觅是一款面向大学生的**路线驱动型旅行搭子匹配 App**。

RouteMe 不是普通交友软件，也不是订票或导航平台。产品以真实旅行计划为连接媒介，让用户从旅行内容中获得灵感，发布自己的行程，发现路线和时间相近的同行者，建立连接，并在旅行结束后分享体验，继续为其他用户提供新的旅行灵感。

> **旅游是产品主题，交友是产品帮助用户完成旅行的核心方式。**

---

## 2. 产品价值闭环

> **旅行灵感 → 发布行程 → 发现同行者 → 建立连接 → 一起旅行 → 分享体验 → 产生新的旅行灵感**

这个闭环比单纯的“发布行程 → 找搭子 → 聊天”更加完整，也更能体现 RouteMe 的 Travel 主题。

### 2.1 旅行灵感

用户可以浏览其他学生公开的旅行计划和游后分享，从中发现目的地、路线和旅行方式。

MVP 中的灵感来源不需要做成复杂的推荐算法，只需提供：

- 公开旅行计划列表；
- 已完成旅行的简单分享；
- 按目的地和日期筛选；
- 兴趣标签，例如摄影、美食、海边、徒步。

### 2.2 发布行程

用户将灵感转化为可执行的旅行计划，填写：

- 目的地；
- 出发及结束日期；
- 简单路线；
- 计划人数；
- 兴趣标签；
- 可选预算和补充说明。

### 2.3 发现同行者

系统根据旅行计划而不是单纯根据个人资料寻找搭子。

首版采用简单、可解释的规则：

- 目的地相同；
- 出发日期相同或接近；
- 兴趣标签相似；
- 行程仍在招募中。

### 2.4 建立连接

用户查看旅行计划和发布者基本资料，提交同行申请。发布者可以接受或拒绝。

只有申请被接受后，双方才能进入文字沟通页面，避免产品变成无条件陌生人私聊工具。

### 2.5 一起旅行

MVP 不需要追踪用户实时位置，也不需要提供导航。产品只需支持旅行前的基础沟通和同行关系状态。

可展示：

- 已确认同行者；
- 集合区域；
- 简单行程；
- 安全提示；
- 退出同行入口。

### 2.6 分享体验

旅行结束后，参加者可以发布简短的旅行体验：

- 文字感想；
- 路线体验评价；
- 可选图片；
- 实际旅行强度；
- 给后续旅行者的建议。

### 2.7 产生新的旅行灵感

游后分享展示在旅行计划详情或灵感列表中。其他用户可以查看该路线的真实体验，并基于原路线创建自己的旅行计划，从而形成循环。

MVP 可提供“参考此行程发布”按钮，将目的地和路线描述带入新建页面，用户再自行修改日期和人数。

## 3. MVP 需要验证的核心假设

> 当大学生看到真实、可参考的旅行计划后，是否愿意发布自己的计划，并通过目的地、日期和兴趣找到合适的同行者？旅行结束后的真实体验，是否能够继续促进其他用户产生旅行计划？

MVP 不需要证明 RouteMe 能完成所有旅游服务，只需要验证以下三件事：

1. 用户愿意发布可被他人理解的旅行计划；
2. 用户愿意基于具体路线申请同行；
3. 游后分享能够成为下一位用户的旅行灵感。

---

## 4. 8 天范围控制

产品闭环完整，不代表每一个步骤都要开发得很复杂。8 天内采用以下范围：

| 闭环阶段 | MVP 实现 | 暂不实现 |
|---|---|---|
| 旅行灵感 | 计划列表、游后分享、标签、筛选 | AI 推荐、无限信息流、热门榜单 |
| 发布行程 | 手动填写目的地、日期和简单路线 | AI 自动生成完整路线、三种模式 |
| 发现同行者 | 目的地、日期和兴趣规则匹配 | 复杂推荐算法、附近的人 |
| 建立连接 | 同行申请、接受或拒绝 | 滑卡匹配、无限私聊 |
| 一起旅行 | 已确认同行者、基础聊天、安全提示 | 实时位置、导航、紧急救援系统 |
| 分享体验 | 文字分享、体验评价、可选图片 | 短视频、直播、复杂内容社区 |
| 新的灵感 | 查看分享、参考此行程发布 | 个性化内容推荐算法 |

## 5. 功能优先级

## 5.1 P0：必须完成

### 5.1.1 演示用户与基础资料

为控制开发量，可提供 2–3 个预设演示账户，不必开发完整注册、验证码和找回密码。

基础资料包括：

- 昵称；
- 默认头像；
- 简介；
- 旅行兴趣，最多 3–5 个标签。

### 5.1.2 旅行灵感首页

首页同时承担“浏览计划”和“发现灵感”的作用。

每张卡片展示：

- 计划标题；
- 目的地；
- 日期；
- 简单路线；
- 兴趣标签；
- 发布者昵称；
- 已加入人数/计划人数；
- 状态：招募中、已满员、已结束。

支持：

- 按目的地筛选；
- 按日期筛选；
- 切换查看“招募中的行程”和“旅行体验”。

### 5.1.3 发布旅行计划

必填：

- 标题；
- 目的地；
- 出发日期；
- 结束日期；
- 简单路线或行程描述；
- 计划同行人数。

选填：

- 集合区域；
- 预算范围；
- 兴趣标签；
- 补充说明。

### 5.1.4 旅行计划详情

展示：

- 完整路线；
- 日期和人数；
- 发布者简介和旅行兴趣；
- 当前同行者；
- 同行申请入口；
- 已结束行程的游后分享。

### 5.1.5 基础路线匹配

首版不做 AI 匹配，使用规则排序：

- 目的地相同：50 分；
- 日期相同：30 分；
- 日期相差一天：20 分；
- 每个共同兴趣：10 分，最多 20 分。

最高 100 分。结果需要显示匹配原因，而不仅是百分比。

示例：

> 匹配度 90%：目的地和日期相同，并且都喜欢摄影。

如果开发时间不足，删除百分比，只保留目的地、日期筛选和共同兴趣提示。

### 5.1.6 同行申请

申请者可以：

- 填写一句申请说明；
- 提交申请；
- 查看待处理、已接受、已拒绝或已取消状态；
- 在处理前取消申请。

发布者可以：

- 查看申请者资料；
- 接受或拒绝申请；
- 达到人数上限后停止接受新申请。

规则：

- 不能申请自己的行程；
- 不能重复申请；
- 已满员和已结束的行程不能申请；
- 只有发布者能处理申请。

### 5.1.7 建立连接与基础聊天

申请被接受后建立同行关系，并开放文字聊天。

只实现：

- 一对一文字消息；
- 发送时间；
- 消息列表；
- 手动刷新或短轮询。

不实现 WebSocket、语音、视频、图片聊天、已读回执和推送通知。

### 5.1.8 我的旅行

统一展示：

- 我发布的行程；
- 我申请的行程；
- 已匹配的同行；
- 已完成的旅行；
- 可分享体验的旅行。

### 5.1.9 最低安全能力

必须包括：

- 取消申请；
- 退出同行；
- 举报入口；
- 不公开电话、证件和精确住址；
- 首次见面请选择公共场所的提示；
- 重要行程告知亲友的提示。

## 5.2 P1：P0 稳定后完成

### 5.2.1 游后分享

最小实现：

- 只能针对已结束且参加过的旅行发布；
- 填写文字感想；
- 评价路线强度：轻松、适中、较累；
- 填写一条给后来者的建议；
- 展示在原计划详情页和灵感首页。

图片上传属于增强项。如果时间紧张，可以只做文字，使用项目内置封面图。

### 5.2.2 参考此行程发布

在已结束行程或分享详情中提供按钮：

> **参考此行程发布**

点击后预填：

- 目的地；
- 路线描述；
- 兴趣标签。

日期、人数和集合地点必须由新用户重新填写。这个功能用很小的开发成本体现“分享体验 → 新的旅行灵感 → 发布新行程”的闭环。

## 5.3 P2：本次不做

- 特种兵、悠闲、临时起意三种模式；
- AI 自动路线生成；
- 新用户 60 秒引导；
- 天气、证件、厕所和超市提醒；
- 地图导航和实时定位；
- 订票、酒店、门票和支付；
- 附近的人；
- 实名认证和复杂信用体系；
- 积分、勋章和商城；
- 短视频和直播；
- 完整推荐算法；
- 复杂无障碍路线计算。

## 6. 核心页面

首版控制为 8 个页面：

1. **演示用户选择页**：选择预设用户进入系统；
2. **旅行灵感首页**：浏览招募中的行程和旅行体验；
3. **发布行程页**：填写目的地、日期、路线和人数；
4. **行程详情页**：查看计划、发布者、同行者和分享；
5. **同行申请页**：提交申请或处理收到的申请；
6. **我的旅行页**：查看发布、申请、匹配和已结束行程；
7. **聊天页**：匹配成功后进行文字沟通；
8. **游后分享页**：P1，填写体验和建议。

不建议为个人资料单独设计复杂页面，可以使用弹窗或简单详情区域。

## 7. 核心用户故事

### US-01：获得旅行灵感

作为一名不知道去哪里的学生，我希望浏览其他学生的旅行计划和真实体验，以便找到适合自己的旅行方向。

**验收标准：**

- 可以看到公开行程；
- 可以查看目的地、日期、路线和兴趣；
- 可以筛选目的地和日期；
- 可以查看已结束行程的体验分享。

### US-02：发布行程

作为一名已有旅行想法的学生，我希望发布目的地、日期和简单路线，以便寻找同行者。

**验收标准：**

- 必填信息校验正确；
- 发布后可在首页找到；
- 发布者可以查看自己的计划。

### US-03：发现同行者

作为一名寻找搭子的学生，我希望找到日期、目的地和兴趣相近的计划，以便减少筛选成本。

**验收标准：**

- 可按目的地和日期筛选；
- 可看到共同兴趣或匹配原因；
- 满员和已结束计划状态清晰。

### US-04：建立连接

作为申请者，我希望申请加入行程；作为发布者，我希望决定是否接受，以便双方在同意后建立联系。

**验收标准：**

- 申请状态完整；
- 不能重复申请；
- 只有发布者可以接受或拒绝；
- 接受后双方进入已匹配状态。

### US-05：旅行前沟通

作为已匹配的同行者，我希望进行基础文字沟通，以便确认集合和行程安排。

**验收标准：**

- 只有匹配成功者可以进入聊天；
- 消息可以保存和重新读取；
- 退出同行后状态正确更新。

### US-06：分享旅行体验

作为完成旅行的用户，我希望留下实际体验和建议，以便其他学生参考。

**验收标准：**

- 只能对已结束并参加的行程分享；
- 分享显示在原计划和灵感首页；
- 其他用户可以参考该行程创建新计划。

## 9. API 建议

- `GET /api/inspirations?destination=&date=&type=`：灵感首页；
- `POST /api/trips`：发布行程；
- `GET /api/trips/{id}`：行程详情；
- `GET /api/trips?destination=&date=`：筛选行程；
- `POST /api/trips/{id}/applications`：申请同行；
- `GET /api/trips/{id}/applications`：发布者查看申请；
- `PATCH /api/applications/{id}`：接受、拒绝或取消；
- `GET /api/my/trips`：我的旅行；
- `GET /api/chats/{tripId}`：读取消息；
- `POST /api/chats/{tripId}`：发送消息；
- `POST /api/trips/{id}/experiences`：发表体验；
- `POST /api/trips/{id}/copy`：参考原行程创建草稿，可由前端预填替代。

## 10. 8 天、三次迭代安排

三次两天迭代共 6 天，另外 2 天用于准备和整合。

### 第 1 天：范围冻结和工程准备

- 确定 P0、P1、P2；
- 完成页面线框图；
- 确定数据库和 API 契约；
- 初始化前后端；
- 创建 3 个演示账户、6 条行程和 2 条分享数据；
- 固定最终演示脚本。

### 迭代 1，第 2–3 天：灵感与发布

完成：

- 演示用户选择；
- 旅行灵感首页；
- 行程列表；
- 目的地和日期筛选；
- 发布行程；
- 行程详情。

**验收场景：**用户浏览到珠海情侣路行程，并参考灵感发布自己的旅行计划。

### 迭代 2，第 4–5 天：发现与连接

完成：

- 基础匹配或共同兴趣提示；
- 同行申请；
- 接受、拒绝和取消；
- 人数限制；
- 我的旅行。

**验收场景：**用户 B 找到用户 A 的计划，申请同行，用户 A 接受，双方建立连接。

### 迭代 3，第 6–7 天：沟通与分享

优先完成：

- 基础文字聊天；
- 退出同行；
- 举报入口；
- 状态和异常处理。

P0 稳定后完成：

- 文字版游后分享；
- “参考此行程发布”。

**验收场景：**匹配成功的用户可以沟通；旅行结束后发布体验；另一用户可以根据分享创建新计划。

### 第 8 天：集成、测试和演示

- 完成端到端测试；
- 修复阻断缺陷；
- 确认演示数据；
- 验证完整闭环；
- 不再增加功能。

## 11. 最终演示脚本

1. 用户 A 在灵感首页看到“珠海情侣路摄影一日游”的体验分享；
2. 用户 A 点击“参考此行程发布”；
3. 系统预填目的地与路线，用户 A 修改日期并发布；
4. 用户 B 按“珠海情侣路 + 周六”筛选行程；
5. 用户 B 看到共同兴趣为摄影，查看用户 A 的计划；
6. 用户 B 填写一句说明并申请同行；
7. 用户 A 接受申请；
8. 双方进入聊天，确认集合区域；
9. 行程结束后，用户 B 发布文字体验和路线强度；
10. 该体验回到灵感首页，成为下一位用户的新旅行灵感。

演示可以用修改测试数据中的日期或“完成行程”按钮模拟旅行结束，不需要真实等待日期到达。

## 12. Definition of Done

功能必须满足以下条件才算完成：

- 前后端流程可实际操作；
- 数据可保存并重新读取；
- 有加载、空状态和错误提示；
- 普通流程与关键异常流程有测试；
- 演示不需要手工修改数据库；
- 主分支可以正常启动；
- 完整闭环至少成功演示一次。

### 最低测试清单

- 必填字段为空不能发布；
- 结束日期不能早于开始日期；
- 用户不能申请自己的行程；
- 同一用户不能重复申请；
- 满员和已结束行程不能申请；
- 只有发布者能处理申请；
- 接受申请后人数正确增加；
- 未匹配用户不能进入聊天；
- 只有参加过的用户才能发布体验；
- 退出或取消后状态正确更新。

## 13. 延期时的功能削减顺序

如果进度落后，依次删除：

1. 分享图片上传，保留文字；
2. 匹配百分比，保留筛选和共同兴趣；
3. “参考此行程发布”后端接口，改为前端预填；
4. 头像上传，改为默认头像；
5. 实时刷新，改为手动刷新；
6. 预算和集合区域。

不得删除：

- 旅行灵感列表；
- 发布行程；
- 浏览和筛选；
- 同行申请；
- 接受或拒绝；
- 匹配后的基础沟通；
- 至少一种文字版游后分享，前提是 P0 已稳定。

如果聊天开发成为阻断，可以降级为匹配成功后的“同行留言区”，但必须限制为已匹配用户。

## 14. MVP 最终产品陈述

RouteMe 路觅的 MVP 是一款面向大学生的路线驱动型旅行搭子匹配产品。用户从公开旅行计划和真实体验中获得灵感，发布包含目的地、日期和简单路线的旅行计划，通过目的地、日期和兴趣发现同行者，提交同行申请，并在双方同意后进行基础沟通。旅行结束后，用户可以分享真实体验，为其他学生提供新的旅行灵感。

RouteMe 通过“旅行灵感 → 发布行程 → 发现同行者 → 建立连接 → 一起旅行 → 分享体验 → 产生新的旅行灵感”形成完整闭环。首版不追求复杂 AI、地图导航或交易能力，而是验证旅行内容是否能够持续促成真实的同行连接。
